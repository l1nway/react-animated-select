# src — design notes

One `##` section per doc-key. A `// [DOC: some-key]` in code points to the `## Some Key` section here.

## Public API

`select.jsx` holds every public component: `Select`, `Option`, `OptGroup`. `index.js` re-exports them, plus `defineOption` from `model.js`, and the plugin objects `chips` (`chip.jsx`) and `paging` (`paging.jsx`), see Plugins.

- `DEFAULT_PROPS` is the single declaration of the Select's props. A prop the consumer leaves `undefined` falls back to its default (`withDefaults`).
- `texts` and `icons` are objects merged with their defaults key by key, the same way: `texts={{empty: 'Пусто'}}` changes one string and keeps the rest. A key set to `undefined` keeps its default; `null` or `false` is a real value (an icon turned off). `useShallowStable` compares both, like `style`, one level deep, so inline objects do not re-render the config readers.
- `RENAMED` maps every removed prop (the old `visibility`, `OpenIcon`, `emptyText`, …) to its replacement. A consumer passing one gets a single dev warning (see Dev Warnings) instead of a silent no-op. It is migration help for the major version and can be dropped one major later.
- The merge runs on every render of `Select` (a few dozen keys); nothing downstream depends on the identity of `props`. The old `useMemo` on `userProps` never hit, since a props object is new on every render.
- `aria-*` and `data-*` props (`ATTR`) are collected into `config.attrs` and spread onto the combobox before the Select's own attributes, so a consumer can add `aria-labelledby`, `aria-describedby` or `data-testid` but cannot break `aria-expanded` or `data-empty`. `attrs` is compared one level deep, like `style`.
- `MODEL_KEYS` never enter the config context. The store consumes them, and the status flags (`disabled`, `loading`, `error`) reach the UI through state. Keeping them out lets inline arrays, callbacks and status toggles change without re-rendering every UI component.
- Everything else goes into the config, which `useShallowStable` keeps stable while the values are equal.
- `ref` is a plain prop (React 19), not `forwardRef`. It is in `MODEL_KEYS`, and `useSelect` exposes the trigger element through `useImperativeHandle`.
- `Collapse` and `Presence` (`motion.jsx`) are internal and will not be exported (decision 2026-10-03). The package sells the Select, not an animation kit: a public export would freeze their props (and `Presence`'s `wait` / `hold`) as a contract, and the animation system is free to change with every step. A consumer who wants the same motion copies the file (the demo site uses the owner's separate `@l1nway/collapse` package, which the library never imports).

## Plugins

`index.js`, `useSelect.js` (`usePlugins`), the `ext` reads in `trigger.jsx` and `dropdown.jsx`. The package is a core plus plugins, all exported from the package root: `import {Select, chips} from 'react-animated-select'`, `<Select multiple plugins={[chips]}/>`. A consumer who never imports a plugin never bundles it (tree-shaking). Since 0.8 the chips are the `chips` plugin: `multiple` without it shows the picked labels as wrapping comma-separated text (see Picks).

- **A plugin is a value, not a registration.** It is a plain object exported by its own module (`chip.jsx`: `export const chips = {Value: ChipsValue}`, `paging.jsx`: `export const paging = {Footer: PagingFooter, request, row}`), and `index.js` only re-exports it. An object literal is pure, so an unused plugin and the whole module behind it are dropped; a `registerPlugin()` call at import time would be a side effect and keep it.
- Why in the plugin file, not built in `index.js`: webpack keeps the whole body of `index.js` once any of its own bindings is used, so `{Select, paging}` also shipped `chip.css` (measured, webpack 5). With pure re-exports every bundler but esbuild drops the unused plugin's JS and CSS. The cost: a `.jsx` file that exports a non-component is not a Fast Refresh boundary, so an edit there is applied through the app module that imports the library (`apps/sandbox/src/App.jsx` in the local sandbox); `eslint.config.js` allows exactly the names `chips` and `paging` (`allowExportNames`), and each plugin file also exports its slot component, which the lint rule needs next to local components.
- **One-way imports.** A plugin imports from the core (`state.js`, `utils.jsx`, `motion.jsx`, `model.js`, `trigger.jsx`, …). The core never imports a plugin file; `eslint.config.js` enforces it with `no-restricted-imports` on `src/**` (plugin files and `index.js` are exempt). A new plugin adds its files to both lists.
- **Two kinds of seams, nothing else.** (1) Component slots: the core renders `<ext.Slot/>` where the slot sits, and the slot may use any hooks. (2) Pure functions: the core calls `ext.fn(...)` inside its own hooks, memos or handlers. **Never a hook called from a core hook**: the plugin list may change between renders (`plugins={multiple ? [chips] : []}`), and a plugin hook would then break the rules of hooks. A seam is added only when a plugin needs it.
- Seams today: the `Value` slot (`chips`, read by `trigger.jsx` in multiple mode; it renders the whole `.rac-value` and takes the props `height`, `enter`, `leaving`, `onLeft`, see Value and Plugin Morph), the `Footer` slot (`paging`, read by `dropdown.jsx`) and the pure `request` and `row` (`paging`, see Paging).
- **Merge.** `usePlugins` stabilizes the array by value (`useShallowStable`: same plugin objects at the same indexes keep the old array, so an inline `plugins={[chips]}` costs nothing) and merges the objects into one `ext` with `Object.assign` in a `useMemo`. Two plugins providing the same field: the last wins, with a dev warning. `plugins` is in `MODEL_KEYS`; the merged `ext` enters the config as a static handle next to `selectId`, stable unless the plugin set changes.
- **The interface is internal.** Only `plugins` and the plugin exports are public API. The fields of a plugin object are a first-party contract that may change in any minor version.
- **Pure annotations.** Every module-level call carries `/* @__PURE__ */` (`memo`, `createContext`): a bundler cannot know that React's functions are pure, so an unused `const Chip = memo(...)` would survive with everything it references. The annotation is a bundler directive, the one comment allowed besides doc-keys and tags. A class component (`Snapshot`) is dropped with its module when nothing imports it.
- **CSS** of a plugin lives in its own file imported by the plugin module (`chip.jsx` imports `chip.css`), see Styles Layer.
- Prop warnings: `deleteInline` / `deleteAlways` on a multiple Select without `chips`, and `hasMore` / `loadMore` / `loadButton` without `paging`, warn once (see Dev Warnings). `multiple` without `chips` is a valid mode and never warns.
- Future features (virtual list, search, sortable chips, motion presets) are written as plugins from their first line.

## JSX Options

`select.jsx`, `Option`, `OptGroup` and `collectOptions`. The JSX options are data, not components: `Select` reads its `children` during render and never renders them. `Option` and `OptGroup` only return `null`.

- `collectOptions` walks `children` with `Children.toArray` and turns them into records in tree order. It descends into arrays, Fragments, `OptGroup` and `defineOption` components (see Define Option). Anything else (text, HTML tags, ordinary components) is skipped with a one-time dev warning (see Dev Warnings). An `<Option/>` inside an ordinary wrapper component is not seen, because the Select never renders its children.
- `Option` renders only when it is misused (outside a Select, or inside a component the Select cannot read), so its render emits a dev warning.
- Why during render: the options are known on the first render, on the server too (see Server Render), and no extra render is needed after mount. The display order is always the tree order, including options inserted later.
- Elements are recognised by the `racKind` tag on the component, not by identity. After a Fast Refresh edit of `select.jsx`, the consumer's elements still point to the old `Option` function, and the tag stays the same.
- The result is memoized on `children` and kept by `useDeepStable`: a parent re-render creates new elements, but equal records keep the previous array, so the model is not rebuilt. `deepEqual` compares the `jsx` elements structurally.
- Id: the `id` prop, otherwise the element's path (`o-2-kx1`: its React key per level, `k` marks a user key). The path is the same on the server and the client. A repeated `id` is made unique in the model (see Selection Identity). Gotcha: unkeyed dynamic options change their path when an option is inserted before them, like any unkeyed React list, so give them a `key` or an `id`.
- The label falls back through `label` → `name` → the text of `children` (`getText`) → `id`. The value falls back to the text of `children`. `userId` (the second `onChange` argument) is `id`, otherwise the value.
- The group comes from the `group` prop, otherwise from the enclosing `OptGroup`. Groups are merged by name across every source (`<Option group>`, `<OptGroup>`, an array `{group, options}`, an item's `group` field): one header where the name first appears (array options first unless `childrenFirst`), all members under it in source order, the `OptGroup` settings applied. An `OptGroup` whose options all name another `group` keeps its empty header.
- `OptGroup` becomes a marker record (`isGroupMarker`) that carries the group's own settings (`disabled`, `className`, `style`). Its name falls back to `texts.emptyGroup`, like a nameless array group, so `collectOptions` takes that text as an argument.

## Define Option

`model.js`, `defineOption(render)`: the supported way to put a reusable option component into a Select.

```jsx
const CountryOption = defineOption(({c}) => <Option value={c.code}><CountryLabel c={c}/></Option>)
<Select>{countries.map(c => <CountryOption key={c.code} c={c}/>)}</Select>
```

- It returns a component tagged `racKind: 'define'` that holds `render`. `collectOptions` calls `render(props)` instead of rendering it and walks the result like children: one `Option`, several, a Fragment, an array, an `OptGroup`, or another defined component.
- Why: the Select learns the options during its own render, so it stays complete on the server (see Server Render). Rendering the wrapper would need a second pass or effects.
- Invariant: `render` is a pure function of props. No hooks and no context in it: it runs inside the Select's render (React's dev build complains about hooks there). Hooks belong in the content (`CountryLabel`), which renders normally inside the option row.
- Rendered on its own (outside a Select), a defined component renders `null`.
- It lives in `model.js`, not `select.jsx`: the Fast Refresh lint rule forbids exporting a non-component next to components.

## Dev Warnings

`utils.jsx`, `warnOnce(key, message)`.

- Each key warns once per page load (once per process on the server), never on every render. Keys name the problem (`text`, `child <div>`, `option outside`), so two different ignored components each warn once.
- Dev detection: `process.env.NODE_ENV !== 'production'`, inside `try`. Consumer bundlers (Vite, webpack, Next, esbuild) replace the expression, so production builds drop the warnings. Where nothing replaces it and `process` does not exist, the `catch` turns warnings off. `/* global process */` tells ESLint the name is intentional.
- Warnings are the only side effect allowed in a render path; they are idempotent thanks to the key set, so StrictMode double renders do not duplicate them.
- Plugins (`useSelect.js`): `no chips` (`deleteInline` or `deleteAlways` on a multiple Select without the `chips` plugin: they act on chips only), `no paging` (`hasMore`, `loadMore` or `loadButton` without the `paging` plugin), `plugin <field>` (two plugins provide the same field). See Plugins. `no loadMore` (`hasMore` without `loadMore`) comes from the plugin's `request`, see Paging.
- Mode switch (`useSelect.js`, keys `switch value` / `switch open`): an effect keeps the last controlled flags (`value !== undefined`, `open !== undefined`) in a ref and warns when one flips after mount, in either direction, like React does for inputs. The first run only records the flags, so mount and the StrictMode effect replay never warn; `null` / `[]` are controlled values and never warn.

## Contexts

`state.js`. The Select's contexts are split by how often they change, so a consumer subscribes only to what it needs:

- `SelectConfigContext`: the merged props plus static handles (`selectId`, `selectRef`, `highlightStore`). It changes only when the consumer re-renders the Select with props that are not equal.
- `SelectActionsContext`: stable callbacks. Their identity never changes.
- `SelectStateContext`: interaction state and the derived option model. It changes on user actions.

All contexts live in one leaf module that imports nothing from the library, so any component can import them without an import cycle. `PresenceContext` is private to `motion.jsx`.

## Compact Reducer

`state.js`, `compactReducer`. It accepts a partial state or an updater that returns one, and merges it. A patch that changes nothing returns the same state object, so React bails out of the re-render. Every `useReducer` in the library uses it; never declare a local merge reducer.

## Store

`state.js`, `createStore`. A minimal external store (`get`, `set(patch)`, `subscribe`) for values that change very often: the hover highlight, chip hover and swipe. Components read it through `useSyncExternalStore` with a selector, so only the subscribers whose selected value changed re-render. `set` with an unchanged patch notifies nobody.

- Every `useSyncExternalStore` call passes a third argument, `getServerSnapshot`, that returns what the store's initial value selects (no highlight, not hovered, no row hold). Without it React throws on the server. See Server Render.

## Stable Hooks

`state.js`.

- `useStableActions(handlers)` returns an object of wrappers created once. Each wrapper calls the latest handler, which is written in `useInsertionEffect`. Consumers can hold the wrappers without re-rendering, and effects that use them need no dependency churn.
- `useShallowStable` / `useDeepStable` keep the previous value while the new one is equal to it. On a real change, they re-render once with the new value. They use the documented "adjust state during render" pattern, so no refs are read or written during render.
- `useShallowStable` compares the config: every key with `Object.is`, and `style`, `texts`, `icons` and `attrs` one level deeper.
- `deepEqual` compares plain data and React elements structurally: two elements with the same `$$typeof`, `type`, `key` and deep-equal props describe the same UI. Depth is capped at 12, so odd or cyclic input returns "not equal" instead of overflowing the stack.

## Select Store

`useSelect.js` is the single store of a Select. It owns the reducer (`initSelectState`), composes `useSelectModel` and `useSelectBehavior`, and returns `state` plus stable `actions` for the contexts.

- Reducer fields: `internalVisibility`, `deleting`, `loadPending`, `toggledGroups`, `internalValue`, `picked` (see Selection Identity). The JSX options are not state: `Select` collects them during render and passes them in (see JSX Options). `internalValue` and `internalVisibility` are used only while the consumer does not control `value` / `open`. Switching a Select between controlled and uncontrolled `value` or `open` is not supported (like a React input): pick one mode for the Select's lifetime, and clear a controlled Select with `null` (single) or `[]` (multiple), never `undefined`. A switch warns once in development (see Dev Warnings).
- Gotcha: `commit` writes `internalValue` only while uncontrolled, so after a switch back to `undefined` the Select shows whatever it last stored in uncontrolled mode (or `defaultValue`), not the last controlled value and not empty.
- Open state: `open` controls the *requested* state when defined, otherwise the reducer does. The shown state is `visibility = active && requested` (see State Semantics). Every open or close the Select wants goes through `setVisibility(next)`, which does nothing when `next` equals the requested state, updates the reducer in uncontrolled mode, and calls `onOpenChange(next)` in both modes. So `onOpenChange` reports exactly the real opens and closes in uncontrolled mode, and the requests in controlled mode; `open` without `onOpenChange` is a Select whose open state only the consumer changes (it replaces the old `ownBehavior`). Internally the state keeps the name `visibility`.
- The guard matters for the forced close below and for keys like Escape on a closed list: without it, `onOpenChange(false)` fired on mount of a loading Select and on every status change.
- The hover highlight changes on every pointer move, so it lives in `highlightStore` (see Highlight), not in the reducer.
- Loading (the `paging` plugin does the work, see Paging): `loadLock` is a synchronous ref guard against bursts of scroll events. `loadPending` is the same flag for the UI. `loadPending` is released when the option count, `hasMore` or `loadButton` changes, or when the Promise returned by `loadMore` settles (resolved or rejected); `loadLock` follows `loadPending` in an effect, so the lock opens only after the render that shows the new options. Without a Promise, a load that brings no new options and leaves `hasMore` unchanged (a failed request) keeps the lock forever, which is why the Promise path exists.
- `loadMoreOnce` calls `ext.request({props, lock: loadLock, setPending})` and does nothing without the plugin. A `loadMore` that throws synchronously releases both at once: the lock directly (the `loadPending` true → false pair lands in one batch and never re-runs the effect) and `loadPending`. The error goes to `reportError` (console and `window.onerror`), not up the tree: `loadMoreOnce` also runs from a layout effect, where a throw would unmount the app.
- An open list takes focus. A closed list forgets its explicit highlight and waits for the next open animation (`ready: false`).
- A Select that stops being `active` (disabled or no options) asks to close (see State Semantics).
- Status props (`disabled`, `loading`, `error`) travel with `state`, not with config. They flip at runtime, and only the root UI reacts to them.

## State Semantics

What `disabled`, `loading` and `error` do. One flag decides interaction: `active = !disabled && hasOptions` (model).

- An inactive Select is never shown open: `visibility = active && requested`, so `aria-expanded` and the panel follow `active` even while a controlled `open` stays `true`. It asks to close (`setVisibility(false)`, so `onOpenChange(false)`) only when `active` turns from true to false (`wasActive`). A Select that mounts inactive (loading, no options yet) with `open` true therefore reports nothing on mount and opens as soon as its options arrive; the old effect asked to close on mount.
- "Has a value" (`hasActualValue`): not `null` / `undefined`, not an empty array, not an empty *plain* object. A `Date` or a class instance counts as a value, although `Object.keys` of it is empty.
- `disabled` blocks, like a native `<select disabled>`: the list closes and cannot open, no handlers, no clear button or arrow, chips are locked (see Chip). The value stays visible (title or chips); only an empty Select shows `texts.disabled` in place of the placeholder. A disabled ancestor `<fieldset>` has the same effect (see Fieldset Disabled).
- `loading` and `error` only report; they never block. With options, the Select opens, selects, clears, and chips delete as usual. Without options it is inactive for that reason alone, exactly like an empty list: no clear button, no arrow.
- Title priority: `selectedText` (with a value), the value, then `texts.error`, `texts.loading` (with dots), `texts.disabled`, the placeholder, `texts.empty`. A value always wins, so no data is hidden by a status.
- `error` covers a failed first load and a failed load-more alike: one state, `data-error` on the root (red border), and a status row `.rac-option[data-error]` with `texts.error` at the end of the list, in place of the loading footer. A consumer who retries clears `error` to get the loading footer back.
- `aria-busy` on the root means "something is loading": `loading`, or a pending `loadMore` (`loadPending`). The theme draws a thin moving stripe at the bottom of the trigger for it (`::after`, `rac-busy`); a static full line under reduced motion. The stripe is theme, one rule to replace or drop. While open, `loading` also shows the loading footer with `texts.loading`.
- Why: a status prop must not destroy the consumer's state. A load-more failure used to make the whole Select unusable although its options were fine.

## Fieldset Disabled

`useSelect.js`: a Select inside `<fieldset disabled>` is disabled, like a native field.

- Detection: the first `input.rac-input` (always rendered, see Form Field) `matches(':disabled')`. The browser applies the native rules, so nested fieldsets and the first `<legend>` exception (its content stays enabled) are right without our own walk. `closest('fieldset[disabled]')` would get the legend wrong.
- The result goes into `fieldsetDisabled` (reducer) and `useSelect` passes `{...props, disabled: true}` down, so the model, behavior and title treat it exactly as the `disabled` prop: `aria-disabled`, no focus, an open list closes (`onOpenChange(false)`), chips locked. A `disabled` prop of `true` wins; the check is skipped while it is on.
- Feedback guard: the inputs take `disabled` from the prop only (`disabled && !fieldsetDisabled` in `FormField`). If they took the merged value, the input would stay `:disabled` after the fieldset is enabled again, and the Select would never come back.
- Reactivity: one `MutationObserver` on every ancestor `fieldset` (`attributeFilter: ['disabled']`), set up in a layout effect on `[props.disabled]`, so a Select mounted inside a disabled fieldset is disabled before the first paint. Moving the Select into another fieldset remounts it in React, which re-collects the ancestors.
- Gotchas: SSR markup shows such a Select enabled until hydration. A `<legend>` moved in or out of first position is not observed.

## Option Model

`model.js` (pure) + `useSelectModel.js` (hook).

- `normalizeOptions` turns the raw `options` prop plus the collected JSX options (`jsxOptions`) into one flat list: plain options, group headers, grouped items, and the optional `tail` (the load-more row of the `paging` plugin, see Paging). The UI and the keyboard both walk this list by index.
- `options` accepts primitives, objects, groups (`{group, options}`), and a bare object without label keys, which is read as a dictionary of options.
- Dictionary: its *values* are the options, each read like an array item; the keys are ignored (not the value, not the id, not the `onChange` id). `{usd: 'US Dollar', eur: 'Euro'}` shows and reports `'US Dollar'` and `'Euro'`. Gotcha: the shape is decided by key names. A plain object with any key named `name`, `label`, `id` or `value` is one option (labelled by the first filled one of them); with an `options` key, or a `group` key and none of those four, it is a group (named by `group` when it is a string, else by its first filled field). So `{usd: 'US Dollar', name: 'Euro'}` is one option `Euro`, and `{usd: 'US Dollar', group: 'Cur'}` an empty group `Cur`. A `key → label` map whose keys can collide with these names belongs in an array.
- Only a *plain* object (`isPlain`: prototype `Object.prototype` or `null`) can be a group or a dictionary. A `Date`, a class instance or any other object is one option: its label comes from the label keys, otherwise from its own `toString` (`Date` gives its date text; the default `[object …]` is skipped), otherwise from its first filled field. The old check treated a `Date` as an empty dictionary and dropped it, and split a class instance into one option per field.
- A JSX option's name is its label, otherwise its `value` as text whenever the value is filled: `<Option value={0}/>` and `<Option value={false}/>` show `0` and `false`, like the array options `0` and `false`. They used to show `texts.emptyOption`.
- JSX options arrive in tree order, which is the display order. `childrenFirst` puts them before the array options.
- Group state: the reducer keeps only `toggledGroups`, the names the user toggled. `expandedGroups` is derived on every model change: a group header that is not disabled is expanded when `groupsClosed === toggledGroups.has(name)`, i.e. by default open, flipped by a toggle. So every group starts in the same state, whatever its source (`{group, options}`, an item's `group` field, `<OptGroup/>`, an `<Option group>`), including groups that arrive later through `loadMore`. A disabled group is always collapsed.
- Gotcha: `groupsClosed` is read on every render, so changing it at runtime flips every group the user has not toggled.
- The collapsed state of a group is not baked into the list. Toggling a group keeps every option object identical, so memoized rows do not re-render.
- `resolveSelection` maps the raw `value` onto the normalized options (see Selection Identity). A value without a matching option becomes a virtual entry (`virtual: true`), so an outside `value` is always shown. Its id is `virtual-<key>-<n>`, where `n` counts the earlier virtual values with the same key; it used to be the position in `value`, so removing one value re-keyed every virtual chip after it, and they all animated out and back in.
- In the hook, `options` and `value` are stabilized with `useDeepStable`, because consumers often pass inline literals. Selection is derived from `value` on every change, so an outside update is reflected at once.
- `commit` is the single exit for a new value: it stores the value only in uncontrolled mode, always stores `picked` (see Selection Identity), and always reports the value through `onChange`.
- Value shape: `onChange` reports each option's `original`, which depends on the source. An array item is reported as given: a primitive as itself, an object as the whole object (`{value: 'pro', label: 'Pro'}`, not `'pro'`). An `<Option/>` (also from `defineOption`) is reported as its `value`, or the text of its children without one. The second argument (`userId`) is the item's `id ?? value ?? name ?? label` for objects, the primitive itself, or the `<Option/>`'s `id`, else its value. A value is matched against the same shape (see Selection Identity), so a value taken from one source does not select the same option written in the other.
- Clearing commits the empty value of the mode: `null` in single mode, `[]` (with ids `[]`) in multiple mode, the same as removing the last chip. The old clear sent `null` in multiple mode, and `value.map` in the consumer threw.
- Picking the option that is already selected in single mode only closes the list, with no `onChange`, like a native `<select>`, Radix and MUI. Single mode has no "uncheck by click"; the clear button, Delete and Backspace are the way to empty it. Multiple mode toggles as before.

## Selection Identity

`model.js` (`resolveSelection`, `claim`) + `useSelectModel.js` (`picked`). The normalizer never rejects user data: duplicates, `NaN`, empty items, circular objects and colliding JSX ids all stay separate, selectable options.

- Invariant: every normalized option has a unique `id`, and the selection is a list of those ids. The value alone cannot say which of `1, 1, 1` (or `true, true`, two equal strings, two `{name: 'x'}`) was picked.
- `picked` (reducer, both modes) holds the ids of the options the user last committed. `resolveSelection` searches the hinted options first, then the whole list, and takes the first free option whose `original` matches the value item. So a hint only decides between equal candidates; a value that no longer matches its hint falls through to the plain search.
- Why not ids only: `value` stays the source of truth for controlled mode. An outside value that is equal to the committed one keeps the user's exact options; a changed one is matched by value, and an ambiguous one takes the first free duplicates in list order.
- Match order: identity (`same`: `===`, plus `NaN` equals `NaN`), then `JSON.stringify` for objects. `toJSON` never throws (circular, `BigInt`) and returns `undefined`, which matches nothing. Only records with an `original` field take part, so a value item `undefined` never matches a group header, the load-more row or an empty placeholder.
- JSX ids come from the `id` prop, which consumers may repeat. `claim` suffixes the repeats (`jsx-same`, `jsx-same~1`) in tree order, so the second one keeps its id while the order holds. Array ids are positional (`default-<depth>-<i>`) and unique by construction.
- Gotcha: a controlled consumer that ignores `onChange` still moves `picked`. With an unchanged, equal value the Select shows the option the user clicked among the equal ones; this is intended, the value cannot tell them apart.
- Gotcha: `onChange`'s second argument (`userId`s) is as ambiguous as the value for duplicates. Consumers who need to tell duplicates apart give them distinct `id`s.
- Gotcha: after the list itself changes (an item inserted or removed before the duplicates) with an unchanged value, equal primitives are matched by position, because the hint is a positional id. Options `[1, 1, 1]`, pick the second `1` (`default-0-1`), remove the first: `default-0-1` is now the old third `1`, so the second row of the new list is selected, not the one the user picked. The same holds for equal strings, `true`, `NaN` and repeated JSX ids (`jsx-x~1`). Objects held by reference are unaffected (identity is tried over the whole list first). Consumers who add or remove items give duplicates distinct `id`s: an `<Option id>` keeps its id across list changes, and an object with its own `id` field is no longer equal to its twin.
- Gotcha: matching never crosses shapes. An object value matches only an object option (`<Option value='pro'>` has the primitive `'pro'`), and a primitive value never matches an array object by its `value` field: both become virtual entries, shown with their own label and no `aria-selected` row (see Option Model, value shape). The JSON match is also key-order sensitive: `{label, value}` does not match an option `{value, label}`.

## Highlight

`useSelectBehavior.js`. The highlight lives in `highlightStore`: `{index, fallback, ready}`.

- `index` is set explicitly by hover or the keyboard. `fallback` is computed: the first selected option that can be reached, otherwise the first reachable option (not a header), otherwise the first reachable header. `effectiveHighlight` is `index`, or `fallback` when `index` is `-1`.
- Reachable (`useReachable`: `reach` plus `list`, the reachable indices in order): enabled, not loading, and either an option outside a collapsed group or the header of a group that has options. Headers are reachable so that the keyboard can open and close groups: with `groupsClosed`, the options of a closed group were unreachable by keyboard before. Enter / Space on a header toggles it (`selectOption` routes headers to `toggleGroup`), and the highlight stays on it. A highlighted header is announced as an option whose name includes its state (see Option List).
- A layout effect with no dependency list runs on every render. It keeps `index` only while it still points at a reachable entry and publishes the new `fallback` before paint.
- **Load row kept.** The effect also keeps `index` while it points at the load-more row of the `paging` plugin (`options[index].loadMore`), loading or not (a loading row is not reachable). Pages are inserted before the row, so when one lands the same index is the first new option: it is highlighted and scrolled into view with `block: 'nearest'` (a few pixels), and the list goes on where the user was. A failed load leaves the count unchanged, so the highlight is back on the row, ready for a retry. When the row disappears (`hasMore` turned off), the index lands on the first new option; with nothing new it points past the end, and `refs.row` (the index kept on the row in the last run) moves it to the next reachable entry, otherwise the last one. Why: the loading row used to drop `index` to `-1`, so `fallback` (the first option) took the highlight and its scroll into view ran the smooth list scroll (`scroll-behavior: smooth` in base) all the way to the top, on click, Enter / Space and tap alike.
- `step` moves over `list`: ArrowUp / ArrowDown by one, cyclically; PageUp / PageDown by `PAGE` (10) without wrapping; Home / End to the ends. While auto loading (`hasMore` without `loadButton`), the arrows do not wrap either, otherwise the user would jump over the loading edge. Home and End also open a closed list (with the highlight already moved); the other keys only open it. From an unreachable position (only the loading row can be one) `step` starts between its neighbours, so ArrowUp goes to the option above the row and ArrowDown wraps to the first, as from the last option.
- `ready` is set when the open animation ends. `OptionItem` scrolls into view only when it is ready, otherwise the collapsed container would be scrolled instead.
- Enter re-sets the current index before selecting, so a changed selection does not move the highlight away from the chosen option.

## Select Behavior

`useSelectBehavior.js`: keyboard, focus and blur. Scroll and load-ahead loading live in the `paging` plugin (see Paging).

- Returning to the browser tab refocuses the select. A window `focus` listener stores a timestamp, and `handleFocus` ignores a focus that comes within 100 ms of it.
- The click that delivered focus must not immediately toggle the list closed again. `justFocused` blocks `toggleVisibility` for 200 ms after the focus.
- Focus opens the list (Tab included): this is a deliberate product decision, not the APG default. Only focus that enters the combobox itself from outside opens it (see Nested Controls).
- A click while in delete mode only leaves delete mode.
- A blur into the portal (`.rac-options`) does not count as leaving the select.
- `onFocus` / `onBlur` report the Select as a whole: `onFocus` when focus comes from outside the combobox, `onBlur` when it leaves both the combobox and the panel. Focus moving between the combobox and its hidden form inputs (see Form Field) reports nothing. Both are `MODEL_KEYS`, so inline callbacks re-render nothing.
- Escape leaves touch delete mode, otherwise closes an open list, and in both cases stops the event (`stopPropagation` + `preventDefault`), so a modal around the Select stays open. On a closed Select it does nothing and lets the event through untouched: the old unconditional `preventDefault` kept a native `<dialog>` from closing. A modal that listens in the capture phase (Radix `DismissableLayer`) still sees the key first; there the consumer filters it in `onEscapeKeyDown`.
- Delete clears the value, like the clear button, and only when `icons.clear` is on. Backspace removes the last chip in multiple mode (only when `icons.remove` is on). In single mode it clears, like Delete. These keys are the keyboard path to the clear and chip delete buttons, which are `tabIndex={-1}`, so Tab never stops on them and they do not take focus from the combobox (a button that gets focus anyway: see Nested Controls).
- The clear button's `clear(e)` stops the event itself, so the click does not reach `toggleVisibility`. No class-name check is needed.
- `onKeyDown` (consumer): called first in `handleKeyDown`, with the React event. If it calls `e.preventDefault()`, the Select skips that key entirely (the composeEventHandlers convention), so a consumer turns off any key, for example Enter / Space / arrows / typeahead while keeping Backspace and Delete. `preventDefault` also cancels the browser default, so never use it for Tab. It runs only while the Select is `active` (the handlers are attached only then) and also sees keys bubbling from the nested buttons. A `MODEL_KEYS` prop: an inline handler re-renders nothing.

## Popup

`popup={false}`: a Select without a panel, for a list of chips that is only shown and pruned (a tag list).

- The root is `role='group'` (named like the combobox: `aria-label`, `aria-labelledby` or the placeholder) without `aria-haspopup`, `aria-expanded`, `aria-controls`, `aria-activedescendant` and `aria-required` (they belong to the combobox role; `trigger.jsx` builds them as one object). `tabIndex` stays, so Backspace / Delete still reach it.
- Nothing opens it: `setVisibility(true)` returns early (no `onOpenChange` call), and `visibility` is `false` even with a controlled `open={true}`. Click, focus, Enter / Space, arrows and typeahead therefore do nothing; `Dropdown` renders `null`; the arrow is hidden.
- Kept: chip deletion (button, Backspace, long press delete mode), clear (button, Delete), chips animations, the live region, form fields.
- CSS keys on the missing `aria-haspopup`, so no new state flag: `cursor: default` in base, no hover tint in the theme.
- Gotchas: the Select still needs `options` (an empty catalogue makes it inactive, see State Semantics); pass the same values as options. `useDropdownPosition` still runs its closed-state observers (the hooks sit above the early return), which only write `data-placement`.

## Nested Controls

`useSelectBehavior.js` (`handleFocus`, `handleKeyDown`), `refocus` in `utils.jsx`, used by the chip delete and clear buttons: a button inside the combobox that does get focus (programmatically, or a screen reader that focuses `tabIndex={-1}` elements) keeps it and handles its own keys.

- React `onFocus` / `onKeyDown` bubble, so a nested button's events reach the root handlers. `handleFocus` opens the list only when the target is the root and focus comes from outside the Select. Before, focusing the delete button opened the list, the open effect in `useSelect.js` pulled focus back to the root, and Enter then toggled the highlighted option: the chip seemed removed by the button, but it was the first selected option.
- `handleKeyDown` ignores Enter and printable keys (Space included) aimed at a nested element: they belong to it (native button activation, typing in custom chip content). Arrows, Home/End, Escape, Tab, Backspace and Delete keep their root meaning; an arrow opens the list, and the open effect moves focus to the root.
- Focus moving inside the Select (a nested button to the root, a hidden form input to the root) neither opens the list nor reports `onFocus`. A form validation focus on the hidden input therefore lands on a closed combobox.
- `refocus(e, selectRef)` moves focus back to the root before the button collapses when the button (or the clicked chip) held it. Without it focus would drop to `body` without a blur event once the button unmounts. A mouse click never focuses these buttons (`onMouseDown` stops the event), so it changes nothing there.
- Gotcha: a delete button shown only on hover collapses when the pointer leaves the chip; if it held focus, focus drops to `body`. With `deleteAlways` the button stays mounted.

## Typeahead

`useSelectBehavior.js`, `typeahead` + `match`: typing jumps to an option by its text, like a native select (WAI-ARIA select-only combobox).

- A printable key without Ctrl / Meta / Alt (and not during IME composition) appends to a query that resets `TYPEAHEAD_MS` (500 ms) after the last key. A closed list opens, with the match already highlighted.
- The search runs over the reachable real options (`'original' in option`: no headers, no load-more row, no placeholders), by `name`, case-insensitive, from the current highlight on and wrapping. A query of one repeated letter (`p`, `pp`, `ppp`) cycles through the options starting with that letter, from the one after the current; a longer query stays on the current option while it still matches.
- Space is a typeahead character only while a query is running (`Pear tree` works); otherwise it keeps its select-or-open meaning.
- Options inside a collapsed group are not searched, like the arrows. The timer is cleared on unmount.

## Collapse

`motion.jsx`, `Collapse`: the only animation primitive. It renders one element (`<div>`, or the tag given in `as`) and animates its whole box on one axis (size, padding, border width and margins, plus opacity with `fade`) when it opens and closes. It has no dependencies: it runs on the Web Animations API (`element.animate`).

### Usage

```jsx
// controlled: `in` decides
<Collapse axis='y' in={open} className='rac-group-items'>{children}</Collapse>

// driven by the nearest <Presence/>: no `in`, a unique `key`
<Presence>
    {items.map(item => <Collapse axis='x' fade key={item.id}>{item.label}</Collapse>)}
</Presence>
```

| Prop | Default | Meaning |
|---|---|---|
| `as` | `'div'` | The rendered tag (`'button'` for the clear and chip delete buttons). |
| `in` | — | Shown or hidden. Omitted: follows the nearest `Presence`; with no `Presence` it is hidden. |
| `axis` | `'y'` | `'y'` animates `height` and the vertical padding, border widths and margins; `'x'` the same with `width` and horizontal sides; `'none'` animates no size (with `fade`: opacity only, no clip, no lifted limits; see Picks). |
| `exitAxis` | `axis` | The axis of the close animation; `axis` is then the open one. A close interrupted by an open reverses on the close axis. Internal, used by the picks (in `'none'`, out `'x'`). |
| `fade` | `false` | Also animates `opacity`. |
| `unmountOnExit` | `true` | Removes the div once closed. With `false` it stays in the DOM, collapsed to 0. |
| `duration` | Select `duration`, else 300 | Milliseconds. Halved for a Presence child marked `swap` (see Presence). |
| `easing` | Select `easing`, else `'ease'` | Any CSS easing. |
| `group` | — | A `Set` shared by several Collapses: they run on one clock (see Collapse Group). Internal, used by the inline chip delete buttons and the titles. |
| `nodeRef` | own ref | Pass a ref when the owner must reach the element (the options panel positions itself through it). |
| `onEntered` / `onExited` | — | Called when the open / close animation really finishes. |
| rest | — | Spread onto the element (`className`, `style`, `id`, ARIA, handlers). |

### How it works

- On every change of the shown state, a layout effect (before paint) measures the natural box with `getComputedStyle` and runs one animation between the collapsed frame (every animated side `0px`, opacity `0`) and the measured frame. Both frames carry `overflow: hidden`, so the element clips its content only while it animates or is held closed.
- The frames also carry `text-overflow: clip` and lift the size limits of the axis (`min-width: 0` and `max-width: none`, or the height pair, `LIMITS`): while it animates, the animation owns the size. The measured target already includes the element's own limits. Without this, an ellipsis would slide along with a growing title, and a consumer `min-width` would stop a collapse halfway. The truncated chips rely on the lifted `max-width` (see Trigger Width).
- Nothing stays in inline styles (the measurement clip is removed in the same read). When an open animation ends, the effect disappears and the element goes back to its natural `auto` size, so later content changes resize it normally.
- Hidden state is held by the finished close animation (`fill: 'both'`). An open animation uses `fill: 'backwards'`. As a result, every animation that ends *open* leaves no trace, and every one that ends *closed* keeps the element at 0 until it is unmounted or reopened. The close fill also covers the *before* phase: Chrome may resolve a new animation's start time a little after the current frame, and for that instant its current time is negative. With `forwards` only, the element would show its natural size in that instant. Group members set their start time explicitly (see Collapse Group), but other Collapses still rely on this fill.
- Interrupting a running animation (open → close before it ends) calls `animation.reverse()`: it plays back from the current point with the remaining time. There is no jump and no new measurement. A Collapse in a `group` restarts instead.
- When a Collapse finishes shown, the finished animation is cancelled. A reversed close keeps its `fill: 'both'`; without the cancel its backwards fill would hold the measured size and the clip, and later content growth would be clipped.
- The target is measured with `overflow: hidden` set inline for the read and restored right after: it is the box the animation renders. At rest, with no vertical padding or border, the first and last child margins collapse through the element and are not part of its `height`; the clipped element is a block formatting context that contains them. Measured without the clip, an open ended short by those margins and they popped out when the clip went. Limit: a collapsed-through margin that also merges with a margin outside the element (a sibling's margin, the element's own vertical margin) still jumps by the merged part.
- `onfinish` is the only completion signal. There are no timers and no `transitionend`. A stale animation (replaced or cancelled) is ignored by the `anim.current === animation` guard.

### Mount rules

- Mounted with `in` true: shown at once, no animation (same as the old `appear={false}`).
- Mounted hidden with `unmountOnExit` true: renders nothing until shown.
- Mounted hidden with `unmountOnExit` false: rendered, held at 0 without animating.
- Hidden, and `unmountOnExit` turns `false`: the element appears held at 0 without animating (the panel with `keepMounted` switched on after mount). The effect re-runs on `unmountOnExit`, and the hold is set whenever the held animation does not target the current element: a ref is not a dependency, so before this the element that appeared later had no hold and rendered at full size, and an element unmounted and rendered again kept the old element's hold.
- Hidden at rest, and `unmountOnExit` turns `true`: an element that never opened unmounts; one that closed while `unmountOnExit` was `false` stays mounted, held at 0, until its next close. Unmounting it right away would need a second "finished" signal next to `onfinish`.
- Mounted by a `Presence` after that Presence's first render: animates in.

### Gotchas

- Collapsed means the whole box is 0 on the axis: size, padding, border and margins. A styled element (a button, the title, a chip) can therefore be the Collapse itself, with no wrapper.
- Collapse adds no class and no permanent CSS. An open Collapse does not clip (focus rings, shadows and the chip shake stay visible), and a consumer's `overflow` or `transition` cannot break the animation.
- Effect reconnects are harmless. React disconnects and reconnects the effects of a mounted component in StrictMode (on mount, and in React 19 also when a keyed child is moved) and inside `<Activity>`. The disconnect does not cancel the running animation and does not reset the "last shown" marker, so the reconnect finds the state unchanged and the animation just continues. An `alive` flag, cleared on disconnect, keeps a finish that lands on a really unmounted Collapse from calling back. (The old version cancelled on cleanup: every chip that React moved lost its animation and snapped to full size.)
- `prefers-reduced-motion: reduce` is read at the moment an animation starts, and it sets that animation's duration to 0. The state still changes through the same path, so hold-at-0, `onEntered` / `onExited` and Presence unmounting all behave as usual, just without motion. A running animation keeps its duration if the setting flips mid-way. CSS transitions follow the same setting through `--rac-duration` (see Styles Layer).
- Without `element.animate` (jsdom in consumer tests), every change completes at once and all callbacks still fire. The rest of the library guards its browser-only APIs the same way (`ResizeObserver`, `IntersectionObserver`, `getAnimations`, `scrollIntoView`), so a Select mounts, opens and selects in jsdom; before, `new IntersectionObserver` threw on every mount.
- Size animations run layout on every frame. That cost is the same for any height or width animation. Keep the animated subtree small.

## Collapse Group

`motion.jsx`, the `group` prop of `Collapse`: several Collapses whose sizes must add up to a known budget run on one clock. The inline chip delete buttons use it (see Delete Reserve): each chip row has room for exactly one open button. The titles use it too: a leaving and an entering title share one row, and two truncated titles sum to exactly its width (see Trigger Width).

- **Rule.** Whenever a member starts or changes direction, every running member restarts from its *current* frame towards its own target, with the same duration and easing. A member that changes direction does not `reverse()`.
- **The current frame is computed, not read.** A restart takes its start values from the member's own keyframes and `effect.getComputedTiming().progress`: `from + (to − from) · progress`, per property. It never reads them with `getComputedStyle`. Firefox handles real pointer input at the start of a refresh tick, after the timeline has advanced but before animated styles are resampled. There, `getComputedStyle` returns the new frame only for elements restyled for another reason (the chip whose `:hover` just changed), and last frame's values for the rest. The mixed start values summed past the budget (measured up to 19.2 px for a 16 px button), and a full row wrapped. Synthetic input (puppeteer, WebDriver) arrives outside the tick and never shows it. The targets (`frame()` of an idle element, or `closed`) have no running animation, so reading them stays safe.
- **The clock is explicit.** Every member animation gets `startTime = timeline.currentTime` (which leaves the pending state) and then `currentTime = 0` (which sets the exact internal timeline time). The timeline time is constant within a task. Starting the animations in the same task is not enough: Chrome resolves the start time of a pending animation on its own, sometimes a frame later than an animation that has just started, sometimes a fraction of a millisecond apart. When the opening button runs ahead of a closing one, the row exceeds the budget by up to about a pixel, and a row filled to the pixel wraps its last chip. `currentTime = 0` matters in Firefox, whose timing getters are coarsened (`privacy.reduceTimerPrecision`, much more under `resistFingerprinting`): a start time set from the coarse `timeline.currentTime` would begin the animation partway in.
- **Why it holds the budget.** With one clock, member *i* has width `wᵢ(t) = fromᵢ + (toᵢ − fromᵢ)·e(t)`, so the sum is `S₀·(1 − e) + S₁·e`: a blend of the sum now (`S₀`) and the sum at the targets (`S₁`). When both are within the budget (at most one target is open), so is every frame, for any easing between 0 and 1, however fast the targets change.
- **Why not `reverse()`.** A reversed animation retraces its curve backwards over the time it has run, while the new member runs its curve forwards. For an asymmetric easing such as `ease` (0.8 at half time), a button caught near the end of its opening and a new button opening sum up to about 1.6× the budget halfway through: the row overflows and its last chip wraps.
- **Why independent timings fail too.** A member that is already closing keeps its own older clock. For strong ease-out curves, that closer and the new pair can still sum above the budget. So every running member restarts, not only the two that changed.
- **Batch skip.** A member started in the current batch is skipped, because it already runs on the clock. A batch is a module-level token that lasts until the next microtask, so it covers one commit's layout effects. Comparing times does not work: Firefox returns a coarsened `startTime` (it gives back 366.82 after being set to 366.84), so the check never matches. Under `resistFingerprinting`, a start time from an earlier frame can match the current time, and skipping that member breaks the clock. A redundant restart in a later microtask of the same task is harmless: it restarts from the same frame. Touch delete mode does not use the group.
- **Rounding.** The sum is exact in real numbers, but layout rounds every member's width on its own: Blink and WebKit truncate to 1/64 px, which can only lose width, while Firefox rounds to the nearest 1/60 px (app unit). With several members, Firefox can therefore exceed the budget by up to half an app unit per member. This is measured at 1–3 app units with 7 members when the device pixel ratio or zoom is not 1. The Delete Reserve absorbs it.
- Membership: a Collapse joins the `Set` when it starts an animation and leaves when that animation finishes or the Collapse disconnects; a reconnect with a running animation joins again.
- An easing that overshoots (a `cubic-bezier` with a y above 1) breaks the bound. The chip buttons use the Select's `easing` like every animation, so such an `easing` with `deleteInline` can wrap a full row mid-handover.

## Presence

`motion.jsx`, `Presence`: replaces `react-transition-group`'s `<TransitionGroup>`. It keeps a child in the DOM after the parent stops rendering it, until that child's exit animation ends. It renders no wrapper element.

### Usage

```jsx
<Presence>
    {showA && <Collapse axis='x' key='a'>A</Collapse>}
    {showB && <Collapse axis='x' key='b'>B</Collapse>}
</Presence>
```

Rules:

1. Every child needs a stable, unique `key`. The key is the child's identity: the same key means the same item.
2. Each child must contain exactly one Collapse **without `in`**. That Collapse reads the child's presence and reports the end of its exit. Collapses with an explicit `in` inside the child ignore the Presence (for example the chip delete button).
3. The child may be any component (`Chip` wraps its Collapse together with a row break). It does not need to forward any props.

`hold` (default `false`): while it is true, a child whose exit has finished stays mounted instead of being dropped; when it turns false, every leaving child is dropped in that same render. The owner must turn it off only once all exits have finished. The chips use it (see Chip Hold), so that a collapsed chip keeps its row until the whole layout is released.

`wait` (default `false`): out, then in. When one change of `children` both drops present keys and adds new ones, the new keys wait: they keep their place in the list but are not rendered until no leaver remains (on the `hold` release, or on the last `onExited` without hold). A key added while others wait also waits. A waiting key removed again (a → b → a) is dropped and never mounts; a revived leaver reverses as usual. Pure removals and pure additions never wait. The chips use it while their animations have a duration (`duration > 0`, no reduced motion; see Chip Hold).

Half time in a swap: the leavers of such a change and the keys that waited for them are marked `swap` (in `PresenceContext`), and their Collapse runs at half its `duration` (an explicit `duration` prop still wins), so out plus in takes one `duration`, like the panel side flip (Dropdown Flip). The mark is cleared at the next change of `children`; a running animation keeps its timing. Pure removals and additions, and leavers that were already leaving, keep the full `duration`.

### How it works

- State: `{children, list}`, where `list` holds `{key, el, present, appear}` in render order.
- When the `children` prop changes, the list is re-synced during render (the documented "adjust state while rendering" pattern, the hooks counterpart of `getDerivedStateFromProps`). Present children take their fresh element. A child whose key vanished stays right after its old neighbour (the nearest earlier child that was present and still is) with its **last element frozen** and `present: false`. Anchoring on the neighbour, not on the old index, keeps several leaving children in their order; the old index-based splice put a leaver after its right neighbour as soon as another child had left or moved, and React then moved DOM nodes. Re-adding a key while it is leaving flips it back to `present`, and its Collapse reverses; it moves to its new place in `children`.
- Each item is wrapped in `PresenceChild`, which provides a memoized `{present, appear, onExited}` through `PresenceContext` (private to `motion.jsx`). The value changes only when that item's own state does, so a `memo` child such as `Chip` is not re-rendered by the group.
- `appear` is `false` for the children of the first render and `true` for everything added later. Collapse reads it only once, at mount.
- `onExited(key)` drops the item. It is a no-op if the key became present again, which guards against a late finish, and while `hold` is on.
- Waiting items are `{…, pending: true}` and render nothing. A re-sync keeps them waiting only while a leaver remains; `release` (after a hold release or a drop) turns them into ordinary items once none remains, and they mount with `appear`, so they animate in.
- Why `wait` is off without motion: with a zero duration the exits end a frame later and nothing holds the rows, so the frame between the drop and the mount would show the trigger empty. With instant animations the swap is instant anyway.

### Gotchas

- The frozen element is never updated. A leaving child keeps the props it had at the moment of removal.
- Keys come from `Children.toArray`, so they carry React's `.$` prefix. They are only compared with each other.
- A child without a presence-driven Collapse never reports its exit and stays mounted forever.

## Value

`trigger.jsx`, `Value` and `Title`, plus `chip.jsx`, `ChipsValue`: the `.rac-value` element, the only wrapper between the combobox root and its content.

```
div.rac-select                 role=combobox + state attributes
├─ div.rac-value               flex-wrap row, observed for its height
│  └─ div.rac-title            (multiple: also span.rac-pick per value; with chips div.rac-chip-slot > div.rac-chip)
├─ button.rac-clear            Collapse as='button'
└─ div.rac-arrow               Collapse, aria-hidden
```

- Two branches. `Value` renders the `chips` plugin's `ChipsValue` (`config.ext.Value`, see Plugins) in multiple mode when the plugin is on; otherwise its own `div.rac-value` with a `Title` (single) or `Picks` (multiple, see Picks). The plugin branch is a different component type, so toggling the plugin remounts `.rac-value`; in multiple mode the switch is animated (see Plugin Morph). `Value` owns the root height memo of Value Height and passes it to the slot, so both branches animate the same root height.
- `Title` is the title `Presence` with its Collapse. It takes `hidden` (the chips or picks are shown), `settle` (the chip hold callback), and, for `Picks` only, `wait` and `children` (the pick Collapses, rendered after the title in the same Presence).
- With chips, the title and the chips have a `Presence` each, the title's first, so switching between them (for example, clearing a multiple value) cross-fades: the chips collapse out while the title collapses in. The title always sits at the start of the first row, which lets the chip rows stay held while the title grows or shrinks there (see Chip Hold).
- The title is itself the Collapse (no inner span). It holds the text and, while it shows `texts.loading` (loading without a value or error), the shared `dots` element from `utils.jsx`. The dots sit on the text baseline because the empty dot boxes give `.rac-dots` a baseline at its bottom edge.
- Title key: the title is text, so the Collapse is keyed by it; with `valueAsOption` (rich JSX, which cannot be a key) it is keyed by the selected option's id (see Option Content). A `-loading` suffix is added in both cases while the dots show. A new key makes the old title leave and the new one enter, so the dots appear and disappear with the title and need no Collapse of their own.
- Known issue (due for the animation rework): the key is the text, so any text change replays the title animation, even when the state did not change: typing into `placeholder` or `selectedText`, switching `texts` (i18n). The plan is to key by the meaning of the title (`error`, `loading`, `disabled`, `selectedText`, `value-<id>`, `placeholder`, `empty`), so a text change updates in place and only a state change or another selected option animates. The chips (by chip key, see Chip Keys), rows (by id) and the load-more row (constant id) do not have this problem.
- A boolean value marks the title with `data-bool='true'|'false'` (colored like boolean options).
- The title is one line, truncated with an ellipsis when it is wider than `.rac-value` (see Trigger Width). The title Collapses share one `group`.
- Delete button probe: while the inline delete reserve is needed and its width is unknown, a hidden `button.rac-chip-del` with the real `icons.remove` is rendered once inside `.rac-value` and measured (see Delete Reserve).
- The chip Collapses and the title Collapse call `settle` on `onEntered` / `onExited`, and the chip `Presence` gets `hold={held}` and `wait`; `Snapshot` (`chip.jsx`, a class component rendering nothing) records chip positions before each chip-list commit and each delete mode change (see Delete Mode), and the label sizes before each `look` change (see Chip Resize). All three belong to Chip Hold.
- `ChipsValue` stays mounted for the whole time the Select is multiple with the plugin, with or without picks, so the chip exits, the title cross-fade, the touch delete exit and the root height animation run on clearing too.

## Picks

`trigger.jsx`, `Picks`: the value of a multiple Select without the `chips` plugin. Each picked label is its own `span.rac-pick` inside `.rac-value`, which is already a wrapping flex row.

- **Wrap.** Labels flow onto new rows instead of one line; a label is truncated (`nowrap`, ellipsis, `min-width: 0`) only when it alone is wider than the row. The root height follows the rows (see Value Height). Before, the labels were one joined string in the title.
- **In by fade, out by width.** Each pick is a `Collapse as='span' axis='none' exitAxis='x' fade` in a `Presence`, keyed by option id. It fades in at its full width (a growing pick would rewrap the row every frame; row animations need the row hold of the plugin, Chip Hold), so the picks after it step aside at once. It leaves by fading and collapsing its width and end margin, so the picks after it slide back instead of jumping when it unmounts; a reversed exit grows back from where it is. Gotcha: a shrinking pick can pull the next row's first pick up into its row before it is gone (no row hold here; accepted for the plain mode).
- **Out, then in.** The title and the picks share the title's `Presence` (`Title` `children`) with `wait` (while `duration > 0` and no reduced motion, like the chips). Placeholder → first pick, clearing, and a value replaced at once (some keys dropped, some added) run the leavers first, then the new ones, each at half `duration`. Side by side, a shrinking placeholder plus a full-width pick would wrap the pick to a second row for the whole animation, and the root height would jump up and back. Consequence: in this branch a title change (placeholder ↔ loading ↔ error) is also out-then-in, not the side-by-side group slide of Trigger Width.
- **Rows.** Rows are one line tall, but the first row sits where the single title sits: `.rac-value:has(.rac-pick)` (also the chips in their pick look, see Plugin Morph) gets `padding-block: (--rac-row − 1lh) / 2`, and `.rac-value` is always `border-box` (also with chips, so `min-height` holds while the Plugin Morph animates this padding to 0), so one row is exactly `--rac-row` and each further row adds `1lh`. Before, a second row made `.rac-value` taller than its `min-height`, the first row lost its centring and moved up by about 7 px while the root grew (found on video in Firefox).
- **Separator.** The comma and the gap are theme, not text: a consumer drops or replaces them in CSS. Every pick has the end margin and the `::after` comma; `data-last` (the last present pick) fades the comma out with a CSS transition on `--rac-duration`. So the comma fades with the pick that comes or goes after it: appending a pick fades in the previous comma, removing the last fades it out, in sync with the pick. A leaving pick keeps its old flags, so nothing moves before it is gone. Before, `:not(:last-child)` switched the comma and the margin at once (the leaving pick is still the last child until unmount). Cost: the last pick keeps the width of its invisible comma.
- Text only: an empty label falls back to `texts.emptyOption`, `selectedText` hides the picks and shows the title, `valueAsOption` does not apply. Limit: no chip keys (Chip Keys live in the plugin), so a pick whose option id changes (a catalog change with the same value) fades out and in.

## Chip Keys

`chip.jsx`, `rekey` + `useChipKeys`: the React key of each chip, kept apart from the option id.

- Why: an option id says where the option sits in the current catalog (`default-0-7`, `jsx-a`, `virtual-1-0`). When the catalog changes and the value does not (options become `[]`, arrive later, reorder), the same value item resolves to another id: a real option turns virtual or back. Keyed by id, every such chip left and a new one entered, so the chips animated out and in although nothing was picked or removed.
- Rule: each chip-list change is matched against the previous keyed list. A chip whose id was there keeps that key. Otherwise it takes the key of a leaving chip with an equal value (`sameValue` from `model.js`: identity, `NaN`, then JSON), first in order. Otherwise its key is its id, suffixed with `~` while that key is still taken.
- Invariant: the id-match goes first, so removing one of several equal chips (`1, 1, 1`) removes exactly the clicked one; the value-match only picks up chips whose id changed.
- The id stays the identity everywhere else: selection, `removeOption`, hover and swipe (`chipStore`), breaks and the ghost (`data-id`). Only the `key` in `ChipsValue` uses the chip key.
- Gotcha: a kept chip that turns virtual keeps its place and only changes content (for example, its JSX with `valueAsOption`); that is intended, the value is the same.

## Value Height

`utils.jsx`, `followHeight`, driven by `useChipLayout.js` (chips) or by the plain `Value` in `trigger.jsx`: when the number of chip rows, the height of a rich title or the value row height from the consumer's styles changes, the root's height animates instead of jumping. No wrapper element and no inline style are involved.

- Who observes. With the `chips` plugin, `useChipLayout` observes `.rac-value` (rules below). Without it, the plain `Value` always observes its `.rac-value` (single, or multiple without chips): one `ResizeObserver` per Select, whose first callback only records. The picks wrap into rows (see Picks), so their row count animates here. A text title is one line, but its height still changes with the consumer's styles (`--rac-row`, `font-size`, `line-height`) and with rich content (`valueAsOption`), and both animate. Until 0.8 every Select ran the chip layout, so this was always on; 0.8 observed only once `valueAsOption` had been on, and a theme switch that changed `--rac-row` jumped (regression found on the demo, `#styling`). `duration` / `easing` reach the observer through a ref, so changing them does not reset the memo. Limit: only the `.rac-value` height is followed; a change of the root's own `padding-block`, `border-width` or `min-height` still jumps (as in 0.7.7).

- The `ResizeObserver` on `.rac-value` reports its natural height. When that height changes, the root's height is animated with WAAPI from what is on screen now (the running animation's value, or the last natural root height) to the new natural height, read after cancelling the old animation. A change mid-way retargets from the current frame, so there is no jump.
- The keyframes also carry `overflow: hidden` (new rows are clipped until the root reaches them) and `align-items: flex-start` (the rows stay anchored to the top while the root grows or shrinks; the buttons keep `align-self: center`). Both apply only during the animation. At rest the root is `align-items: center`, so a consumer's fixed height keeps the value centered.
- The height animation always takes the full `duration`, also in a chip swap (Chip Hold, out then in): only the chip enter and exit animations are halved there. The root keeps its height during phase 1 and starts once the final rows are known (phase 2), so it ends at 1.5 × `duration` after the click while the chips end at 1 ×; the new rows are clipped by the root until it reaches them. Before, it ran at `duration / 2` with the entering chips (`BUGS.md` "The Select height animation is shortened together with the chip animations"; measured at `duration` 1000: 500 ms before, 1000 ms after, starting about 540 ms after the click in Chromium and Firefox).
- **Started in the commit, not by the observer.** Chip rows change in commits the `ResizeObserver` sees too late: the breaks of a `freeze` render in a second, synchronous commit after the chip effect has already measured, and `settle` releases the hold inside a Collapse `finish` event, which the browser dispatches before `requestAnimationFrame`. The observer runs after the frame callbacks, so `useDropdownPosition` placed the panel against the new height, then the observer started the root animation from the old one: for a frame the panel covered the lower rows (or left a gap), and the page's scroll anchoring moved the page twice. A layout effect on `breaks` and `held` therefore calls `followHeight` in the same commit (once a height is stored, not during a resize); the observer then finds the value recorded and does nothing. Measured (Chromium and Firefox, 380 px Select, a chip that opens a third row): root 60 → 88 → 61 → … → 88 before, 60 → 61.1 → … → 88 after; removing it 88 → 60 → 86.9 → … before, 88 → 86.9 → … after.
- **During a chip resize** (see Chip Resize) the `.rac-value` height changes every frame. Following it would retarget the root every frame, lag behind the chips and clip them. Instead the target is given once: `freeze` measures the ghost at its natural height (`hold.fit`), and `followHeight(…, pin)` reads the root's natural height with `.rac-value` pinned to that height for the read (`height` + `box-sizing: border-box`, removed in the same call). Invariant: while a `rac-resize` animation runs, `layout` ignores `ResizeObserver` and font callbacks and any `followHeight` call uses `hold.fit`; when the last resize ends, `layout` runs once more and records the heights. Each row's height is the largest of its chips' heights, each moving linearly with the shared easing, so the content stays under the straight line between the start and end heights: the root never clips a chip during the resize.
- Heights are read with `getComputedStyle`, which keeps the math right for any `box-sizing`. A root with a fixed height gives equal start and end values, and no animation runs.
- Why not CSS `interpolate-size`: a transition starts only when the computed value changes. Here the height stays `auto` and only the content changes, so no transition would ever start.
- No reads on mount. The first measurement comes from the first `ResizeObserver` callback of `.rac-value`, after the browser's own layout, and only stores the heights (`memo.value`, `memo.root`). Layout effects call `followHeight` only once a height is stored, so a page mounting many Selects does not force a layout of the freshly committed tree inside the React commit. Without `ResizeObserver` (jsdom) the observer effect measures once instead. Exception: a Select that mounts with chips and `deleteInline` measures its delete reserve before paint (see Delete Reserve); a later row shift would loop the observer.
- Skipped on the first measurement (nothing to animate from), without `element.animate`, and under `prefers-reduced-motion: reduce`. An element with no size (a hidden Select) gets no observer callback and stays unmeasured until it is shown.

## Trigger Width

`base.css` + `chip.css` + `chipGeometry.js` (`ghostRows`) + `trigger.jsx`: the Select never gets wider than its container. Where the consumer's layout sizes it by content (a flex item, an `auto` grid column, `width: fit-content`), it grows with the title and the chips; once it hits the limit, the title and every chip are truncated with an ellipsis.

- **Root.** `max-width: 100%` (never wider than the container) and `min-width: 0` (a flex or grid parent may shrink it below its content; a flex item's default minimum would be the widest text).
- **Title.** `max-width: calc(100% - 0.25px)`, `overflow-x: clip`, `text-overflow: ellipsis`. `clip`, not `hidden`: only the inline axis is cut, so rich content (`valueAsOption`) keeps its vertical overflow, and the title is no scroll container. While a title animates, its frames switch to `text-overflow: clip` (see Collapse), so the ellipsis appears when the title comes to rest instead of sliding with its width.
- **Two titles in one row.** A change of title puts the leaving and the entering one side by side in the first row. When both are truncated, their widths add up to the whole row, and a row that overflows by a fraction wraps the new title to a second line for a frame: the trigger jumps in height. The title Collapses share one `group` (see Collapse Group), so their sum never exceeds the row in Blink and WebKit, which truncate widths; the 0.25 px keeps Firefox's rounding to the nearest app unit inside it too.
- **Chips.** `.rac-chip-slot` is `max-width: 100%` of the row. `.rac-chip` is `max-width: inherit`, `box-sizing: border-box` and `flex-shrink: 0`: it takes the slot's `100%` at rest, and its label `.rac-chip-text` shrinks with an ellipsis (the delete button does not shrink). While the slot animates, Collapse lifts its `max-width` to `none` (see Collapse); the chip inherits `none`, keeps its natural width and is clipped by the slot. A chip that shrank with the slot instead would show an ellipsis sliding along with every enter and exit. A truncated chip's end margin sticks out of its slot, invisibly: it is alone in its row.
- **Growth before the row math.** The chip ghost of Chip Hold and Delete Reserve is laid out in the flow, in place of `.rac-value`: for the moment of the measurement the real `.rac-value` is `position: absolute` (out of the flow, CSS animations keep running, nothing paints in between). The root then takes the width it will have with every chip at full width, whatever the consumer's layout is, and the rows and breaks are computed for that width. The ghost keeps the real height, so the page does not move vertically.
- Why: the old ghost was `position: fixed` at the current width. A Select about to grow put an entering chip onto a new row, grew, then FLIPped the chip back up. With inline delete, the reserve wrapped the last chip of a single row that had room, and hovering flickered between one and two rows every frame (measured in the sandbox, `frame: fit` + `deleteInline`).
- Why the root width needs no pinning: in a content-sized root, the width follows the chips' current widths every frame, so it is never narrower than a held row; in a root of fixed width, the ghost width is the current one.
- **Gotchas.** A wrapper that shrinks to fit without being a flex or grid parent (`inline-block`, a float, `width: fit-content` on the wrapper) takes the widest text as its minimum and overflows; give that wrapper `max-width: 100%`. Rich content (`valueAsOption`) is clipped, not ellipsized: in a chip, `.rac-chip > .rac-option-jsx` is `min-width: 0; overflow-x: clip` like `.rac-chip-text`, so wide content shrinks with the chip and the delete button stays inside it. A truncated title or chip shows its ellipsis only once its animation has ended, a one-frame change. Each ghost measurement lays out the root's ancestors once more (on chip changes during animations, resizes, font loads).

## Trigger

`trigger.jsx`, `Trigger`: the `role='combobox'` root of the Select (`role='group'` with `popup={false}`, see Popup). It renders `Value` and the clear and open buttons. `Dropdown` is its sibling in `Select`, so React events from the portal panel never bubble into the combobox handlers.

- Keyboard, focus, click and blur handlers are attached only while the Select is `active` (not disabled, and has options; see State Semantics). The clear button needs `active` and a value; the arrow needs `active`.
- The clear button and the arrow are root children in one `Presence`. Each is itself an x-axis `Collapse`, so it collapses in and out on its own, with no shared wrapper.
- The clear button is a real `<button type='button'>` named by `texts.clear`, with `tabIndex={-1}`. Delete and Backspace are its keyboard path (see Select Behavior). It stops `mousedown`, so clicking it does not move focus. The icon inside is decoration: the default icons carry `aria-hidden`.
- The arrow is `aria-hidden`. Its rotation is pure CSS from `aria-expanded` and `data-placement` (see State Attributes).
- `data-placement` on the root is written by `useDropdownPosition`, not rendered (see Dropdown Position).
- Accessible name: `aria-label` or `aria-labelledby` from the consumer (see Public API), otherwise the placeholder as `aria-label`. A `<label htmlFor>` cannot name it: a `div` is not a labelable element, so the `id` prop is for `aria-labelledby` of other elements, tests and anchors. `required` adds `aria-required`. While `error` is on, `aria-describedby` adds the error text id (see Live Region) to a consumer's own value.
- `aria-controls` points to the listbox id (`${selectId}-listbox`, set in `Dropdown`). `aria-activedescendant` is the DOM id (`optionDomId`) of the highlighted option while the list is open, otherwise it is absent. It is read from `highlightStore` with a selector that returns the id string, so `Trigger` re-renders only when the active option changes, and its `memo` children do not.

## Form Field

`trigger.jsx`, `FormField`: the Select takes part in a native `<form>`: always reset with it, submitted with `name`, validated with `required`.

- One `input.rac-input` per selected value inside the root, all with the same `name` (`FormData.getAll(name)` reads a multiple value). The value is `original` as text; objects are sent as JSON (`toJSON`, non-throwing). An empty single Select sends one empty field (`name=`), like a native `<select>` on an empty option; an empty multiple Select sends nothing, like `<select multiple>`.
- There is always a first input, so every Select inside a `<form>` belongs to it, like a native field without `name`. A Select that neither submits nor validates (no `name` and no `required`, or an empty multiple without `required`) renders exactly one empty field without `name` and with `hidden` (the form anchor): not submitted, not validated, no layout box, but it still has `form` and `:disabled`. Only the anchor is `hidden`: a `display: none` field cannot show the validation bubble, so the browser would block the submit silently.
- `required` goes onto the first input, so an empty Select blocks the submit and the browser shows its bubble. An empty multiple Select renders one empty field for that. `disabled` disables the inputs: they are not submitted and not validated, as for native controls.
- The inputs are real (not `type='hidden'`, which never validates, and not `readOnly`, which is barred from validation): absolutely placed over the root, `opacity: 0`, `pointer-events: none`, `tabIndex={-1}`, `aria-hidden`, with a no-op `onChange`. The bubble points at the Select. When the browser focuses an invalid input, it hands the focus to the combobox at once.
- `form` prop: the id of the owner form, set as the `form` attribute on every input (the anchor too), like `<select form='id'>`. It overrides the enclosing `<form>`, so a Select outside its form, or inside another one, submits and resets with that form.
- Reset: `FormField` listens to `reset` in the capture phase on the input's root node (`getRootNode()`: the document, or the shadow root, since `reset` does not cross it) and acts when `e.target === input.form`, read at event time. One listener per Select. Why not on the form itself: with the `form` prop the owner may mount after the Select, be replaced, or change its id; `input.form` always resolves the current owner. Capture also sees the event before any listener could stop its propagation. On reset the value goes back to the current `defaultValue` (like a native field, whose `defaultValue` React keeps in sync), or to empty (`null` / `[]`) without one; the panel closes and delete mode ends. Controlled or not, the Select commits it through `onChange`, with the ids resolved like a fresh mount (`picked` empty, so among duplicates the first wins). A Select already at that value with the same picked options fires nothing. React 19 `<form action>` and `requestFormReset()` call `form.reset()`, so they work too.
- Why `setTimeout` and not a microtask: a reset from a click is dispatched by the browser, so microtasks run right after each listener, before React's root listener can call `preventDefault` in `onReset`. The timeout reads `defaultPrevented` after the whole dispatch: a cancelled reset changes nothing. The timer is cleared on unmount and on the next reset. The cost: native fields are reset when `form.reset()` returns, the Select one task later (plus its render), so `new FormData(form)` read synchronously after `reset()` still has the old Select value.
- Why a controlled Select also resets: its owner cannot see a native reset otherwise. A controlled React `<input>` ignores reset; here the native result (fields back to their defaults) is the useful one.
- Invalid state: `onInvalid` on the inputs (only the first one is `required`, and `invalid` does not bubble) calls `markInvalid`, which sets the `invalid` flag (reducer). The root shows `data-invalid` and `aria-invalid='true'` while the flag is set, `required` is on, the Select is empty and not disabled. So nothing is red before the first failed submit (or `checkValidity()` / `reportValidity()`, which fire `invalid` too); a pick hides it, clearing again shows it; reset clears the flag. A consumer `aria-invalid` (server-side errors) is kept when the Select has no flag of its own.
- Bubble text: `texts.required` (default none: the browser's own localized text, the text input's "Please fill out this field"). When set, a layout effect in `useSelect.js` calls `setCustomValidity(texts.required)` on the first input while `required` and empty, and `''` otherwise, so the input never stays invalid after a pick. With a custom text `validity.valueMissing` becomes `customError`.
- `autoComplete='off'` on the inputs: they are plain text inputs, and an autofill by `name` (`country`, `email`) would change the DOM value behind React's back, so the form would submit a value the Select does not show. The `hidden` anchor is never autofilled.
- Gotchas: a Select outside any `<form>` and without the `form` prop has an anchor with `form === null` and no reset; a `form` id that matches no form behaves the same. A later `defaultValue` changes only the reset target, never the current value (as with React inputs). A value without an option (virtual) is submitted as well.

## Live Region

`liveRegion.jsx`, `LiveRegion`: announces changes that a screen reader would not read on its own. Rendered once in `Select`, as a sibling of `Trigger` (not inside `role='combobox'`, so its text never becomes part of the combobox value).

- Markup: `div.rac-live` (visually hidden, `base.css`) with the region `aria-live='polite' aria-atomic='true'` and, while `error` is on, `#${selectId}-error` with `texts.error`. The combobox gets `aria-describedby` with that id, joined with a consumer `aria-describedby`.
- Client only: `useSyncExternalStore` with a server snapshot of `false`, so the SSR markup and the hydration render have no region; it appears right after hydration, empty, before any message (a region inserted together with its text is often not read).
- No announce calls anywhere else: the component diffs `SelectStateContext` itself. A change of `selected` / `selectedIDs`, of the option count (records with `original`: no group headers, load-more row) or of `error` arms a 250 ms trailing debounce; the message is the difference between the snapshot taken when the burst started and the state when the timer fires. So three quick Backspaces read as one "Removed A, B, C".
- Messages, joined by `. `: the selection became empty → `texts.cleared`; in multiple mode chips gone → `texts.removed` (`{label}`: their labels joined by `, `) and chips added → `texts.selected` (`{n}`: the total now selected); the option count grew while the list is open and was not `0` → `texts.loaded` (`{n}`: how many arrived); `error` turned on → `texts.error`. A single-mode pick is not announced: focus is back on the combobox and the reader reads its new value.
- Only user changes: a change is announced only while focus is inside the root (nested buttons included) or touch delete mode is on (it focuses the Select). Otherwise the snapshot just moves on, so an async `value`, a programmatic change, a `form.reset()` from a button or an error of a Select elsewhere on the page stays silent. A burst that started engaged is finished even if focus leaves.
- Texts are templates (`{n}`, `{label}`, replaced with a function, so `$` in a label is safe) or functions `(value) => string` for plural forms.
- The same message twice gets a trailing no-break space, so the reader treats it as a change; the text is wiped after 5 s, so a virtual cursor does not find a stale message. Both timers live in one ref and are cleared on unmount.
- Gotchas: a mouse click on a chip delete button does not move focus (`mousedown` is stopped), so it is announced only if focus already was in the Select. The `aria-describedby` id is rendered on the server while the error element appears after hydration.

## Dom Ids

`utils.jsx`, `optionDomId(selectId, optionId)`: the one format for the DOM ids of options and group headers. `OptionItem` and `GroupHeader` use it for `id`, `Trigger` for `aria-activedescendant`, and the group containers for `aria-labelledby`, so all of them always match.

- The option id is escaped, not cleaned: ASCII letters, digits and `-` stay, every other character becomes `_<code point in base 36>_` (`jsx-a b` → `jsx-a_w_b`). `_` itself is escaped, so the mapping is injective: different option ids always give different DOM ids. `selectId` (from `useId`) contains no `-`, so the first `-` separates it and ids of two Selects never collide either.
- Why: the old `makeId` lowercased and dropped characters, so `id='A'` / `id='a'`, `a.b` / `ab` or a repeated `a` (`a~1`) and `a1` got one DOM id, and `aria-activedescendant` pointed at the wrong row. Group headers used their raw name as `id`, not scoped by the Select: two Selects with the same group names repeated ids, and a name with spaces was no valid id.
- Deterministic: the same option id gives the same DOM id on every render and on the server, so SSR markup and ARIA references stay stable.
- The label of a group header (`.rac-group-text`) has the header's DOM id plus `_l` (`groupLabelId` in `optionList.jsx`). It never collides with an option's DOM id: an escaped id contains `_` only in closed `_<code>_` pairs, and `_l` is never closed.

## Chip

`chip.jsx`. `Chip` is the Presence child: an x-axis `Collapse` with `fade` (`.rac-chip-slot`, `data-id` = the option id, `unmountOnExit={false}`), plus a `rac-spacer` row break after it while Chip Hold says so. `SelectedItem` is the chip itself (`.rac-chip`).

- The delete control is a `Collapse as='button'` (`.rac-chip-del`) named `${texts.remove} ${name}`, with `tabIndex={-1}`; Backspace is its keyboard path. Its inline-or-overlay placement comes from CSS through the root's `data-deleting` / `data-inline-delete`, not from inline style. Two independent props: `deleteInline` picks where it sits (inside the chip, which widens, instead of over its end), `deleteAlways` when it shows (always, instead of on hover; swipe and delete mode show it either way). Only inline-on-hover buttons share one `group` (outside delete mode, see Collapse Group); inline-always buttons are plain chip width and need no reserve. A change of placement or of when it shows is animated (see Delete Mode); the button calls `settle` on `onEntered` / `onExited` for that. Without `icons.remove` there is no delete control at all: no button, no Backspace, no long press.
- `.rac-chip-slot` stays a separate element around `.rac-chip`: the slot is the animated box, the chip is the styled one (margins, shake, hover color).
- The slot carries `data-id`, not `id`: option ids are not unique across Selects on one page, and a DOM `id` could also collide with the page's own ids and styles.
- `Chip` reads its break flag from `chipStore` (`breaks.includes(id)`), not from a prop: a leaving chip is a frozen Presence element and never gets new props, but it may still have to own a break.
- The chip shows the option's text in `.rac-chip-text` (the element that truncates, see Trigger Width), or with `valueAsOption` its content plus its `className` and `style` (see Option Content).
- One `chipStore` subscription in `SelectedItem` returns two bits: hovered and swiped.
- While the Select is not `active` (disabled or no options), chips are `locked`: no hover, touch or click handlers, and the delete button is shown only with `deleteAlways`, as a `disabled` button, so the chip widths and rows stay put.
- Hover has no delay. `mouseenter` takes the hover at once; a leave clears it only if it still belongs to this chip, because a neighbour may already have taken it over. No delay is needed: a hovered chip only grows to the right (its button is at its end), and a closing button to its left shrinks it back by at most as much, so the chip never slides out from under the pointer, and hover cannot flicker. Hover works during a hold as well: the reserve is part of the held rows.

## Touch Target

`base.css` + `chip.css`: on a device with any coarse pointer, the clear button and the chip delete button get a hit area of at least 24×24 px (WCAG 2.2 SC 2.5.8), with no change to layout.

- An absolutely positioned, transparent `::before` with `inset: min(0px, 50% - 12px)`: each axis is padded up to 24 px around the button's centre, and a larger button keeps its own box. A pseudo-element hit-tests as its button, so the click, `mousedown` and the touch events bubbling to the chip (long press, swipe) work unchanged. `.rac-chip-del` is always positioned (absolute in overlay mode, relative inline); `.rac-clear` gets `position: relative`.
- `.rac-arrow` is `pointer-events: none` there: its `rotate` makes it a stacking context, which painted it over the clear button's area. A tap on it still reaches the root and toggles the list.
- `any-pointer`, not `pointer`: hybrid devices (touch laptops) get it too; a mouse-only desktop is unchanged. 24 px, not 44: at 44 the clear area covers the arrow and the chip delete area reaches the rows above and below.
- Gotchas: neighbours later in the DOM that are positioned or transformed (the next chip, a shaking chip) still win where they overlap. A truncated chip's inline delete button sits next to the clear button (centres 20 px apart), so their areas overlap by 4 px and the clear button wins there. Collapse frames clip the area while the button, its chip slot or the root height animates. No `z-index`: a transparent area above a sticky page header would steal taps.

## Touch Delete

`chip.jsx` + `useChipLayout.js`. Delete mode is the touch alternative to hovering a chip.

- A long press (`LONG_PRESS_MS`, 600 ms) on a chip enters delete mode (only while `icons.remove` is on): `setDeleting(true)`, the select takes focus, the list closes, and the device vibrates if it can (`navigator.vibrate(50)`: Android browsers only, iOS Safari has no web vibration). A move of more than `JITTER` (10 px) cancels the pending long press, so a trembling finger still gets it; `touchcancel` cancels it too.
- A horizontal swipe of more than `SWIPE` (30 px) to the left reveals the chip's delete icon; a swipe back hides it.
- `touch-action: pan-y` on `.rac-chip`: the browser keeps vertical page scrolling and hands horizontal moves (the swipe) to the chip. The old `none` froze the page for any touch that started on a chip, which in a full trigger is almost every touch.
- In delete mode (`data-deleting` on the root), every chip shakes (not under `prefers-reduced-motion`) and shows its delete icon, and a tap removes the chip. The release that ends a long press never removes: `onTouchEnd` calls `preventDefault()` when the long press has fired, so the browser creates no click from that touch, whether the finger was on the chip or on its delete button. The `longPress` flag lives only within one touch and is reset on `touchend` / `touchcancel`. No click handler checks it, so a mouse or keyboard click is never swallowed, even after a long press that ended without a click (finger slid off).
- Delete mode keeps the dropdown closed and cancels any hover. It ends by itself once the last chip is gone or the Select stops being `active`, and a click on the trigger or a blur also ends it.
- Entering and leaving are animated without a reflow mid-way: the buttons open or close in the flow and the rows are held (see Delete Mode). The clear button and the arrow are hidden in delete mode, so the row width changes at the same time as the chips.

## Chip Geometry

`chipGeometry.js` + `chipMotion.js`: the pure DOM helpers of the chip area, with no React and no state of their own. `chipGeometry.js` is the layout: `slotsOf`, `rowsOf`, `ghostRows`, `restBreaks`, `freeze`, `snapRows`. `chipMotion.js` is the animation: `isBusy`, `isResizing`, `snapOf`, `flip`, `resizesOf`, `resize`, `padOf`, `repad`, and the delete button placement (`shift`, see Delete Mode); it imports `slotsOf`, never the other way. Split on 2026-10-05, when the plugin morph took the single file past the limit. `followHeight`, `reducedMotion` and `watchMotion` (the reduced-motion subscription behind Presence `wait`) live in `utils.jsx`: the plain `Value` of the core uses `followHeight` too, and the core never imports a plugin file (see Plugins). The resize frames repeat Collapse's `LIMITS` as a literal: `motion.jsx` exports components only (fast refresh). `useChipLayout.js` owns the store, the refs and the effects and calls them. They touch the DOM, so they run only in effects and handlers (SSR-safe), and the ones that write state take the store or the memo object as an argument.

## Chip Layout

`useChipLayout.js`: the layout state of the chip area. `useChipLayout(chips)` takes the chips `ChipsValue` renders (`selectedIDs`, or none while the title is shown). It runs only in a multiple Select with the `chips` plugin; before 0.8 every Select ran it, single ones included (an observer, a fonts listener, three store subscriptions and six layout effects each).

- `layout` runs in a layout effect when the chips or the delete reserve change, on every `ResizeObserver` callback of `.rac-value`, and when a web font finishes loading (`document.fonts` `loadingdone`: a font swapped in after the first paint changes chip widths without resizing `.rac-value`). It re-freezes a running hold, drives the root height (see Value Height) and, at rest, sets the resting breaks (see Delete Reserve).
- The current chips and reserve are passed to `layout` through `holdRef`, written by the effect itself, not read from the effect event's closure: in React 19.2 an effect event called from a layout effect of the same commit still sees the previous render's values. `duration` and `easing` go through `holdRef` as well (a layout effect on them): measured in the sandbox (React 19.2.3), the effect events of `useChipLayout` kept their mount-time closure for good, so a `duration` changed after mount left the root height animation at the old duration. Callbacks created in effects (the resize `onfinish`) call `settle` from the effect closure, not through an effect event.
- Rows are grouped by vertical overlap (`rowsOf`, `chipGeometry.js`): a slot starts a new row when its top is at or below the bottom of the row so far. Equal `offsetTop` is not a row test: with `align-items: center`, a shorter chip (or a tall JSX chip) in the same row has a different top.
- Chips are found as the `.rac-chip-slot` children of `.rac-value` (`SLOT`), identified by `data-id`.
- `chipStore` holds hover and swipe (`hoverId`, `swipedId`) and the break state (`held`, `breaks`). Each subscriber selects a primitive, so only the chips involved re-render.

## Chip Hold

`useChipLayout.js` + `chipGeometry.js` + `chipMotion.js` + `chip.jsx`: chips animate their width, yet no chip ever changes rows in the middle of an animation. Rows change only in discrete steps, and each step is animated as a move (FLIP).

**Why it is hard.** In a wrapping flex row, a chip whose width animates reflows everything after it on every frame. A growing chip at 0 px fits at the end of a full row, then wraps once it grows. A shrinking chip in the middle pulls the tail of its row left, and as soon as the gap is wide enough, the first chip of the next row jumps up, then the next row's first chip, and so on. The old spacer logic patched two of these cases with a px-wide spacer computed once from the widths, so it broke with several rows, several animations at once, or a chip leaving while it owned the spacer.

**Hold.** When the chip list changes while a Collapse is animating, the layout is *held* (`freeze`):

1. `ghostRows` clones `.rac-value` into an invisible ghost (same classes, same height, an end padding of the delete reserve) and lays it out in the flow, in place of `.rac-value` (see Trigger Width), so ancestor selectors apply and the ghost gets the width the Select will have. A clone carries no Web Animations, so every chip in it has its full natural width: entering chips already grown, leaving chips not yet shrunk, finite CSS animations finished. The browser wraps that ghost itself, so there is no width math.
2. Row ends of the ghost become `breaks`: a `rac-spacer` after the last chip of every row but the last. The break is `flex-basis: 100%`, `height: 0`, plus 1 px of end margin: its own zero-height line that nothing can join. Without that 1 px, a chip that has collapsed to exactly 0 px still fits next to a 100% break, joins its line and gives it a height, which pushed every lower row down.
3. During the hold every chip is no wider than in the ghost (growing chips have not reached their width, leaving ones only shrink), so no row can overflow, and the breaks keep any row from pulling chips up. The rows stay exactly as in the ghost for the whole animation.
4. A change during a hold runs `freeze` again. The ghost is rebuilt with the breaks derived from the *held rows* (ids, `holdRef.rows`), not the breaks in the DOM: a break owned by a chip that has moved (a re-added leaver) would otherwise move with it. Held rows can split (a chip inserted in the middle overflows its row), never merge.
5. While held, `Presence` keeps collapsed leavers mounted (`hold`, chips use `unmountOnExit={false}`): a 0 px chip still holds its row's height, so a row made only of leavers does not vanish under the rows below it.
6. A width change of `.rac-value` during a hold (the `ResizeObserver`), a change of the delete reserve or a font swap runs `freeze` again.
7. **Out, then in.** A commit that removes chips and adds others (a whole new `value`, a partial replacement) runs in two phases (`Presence` `wait`). Phase 1: only the leavers collapse, under a hold built from the current rows, so the root keeps its height. Once they are gone, `settle` releases the hold, the waiting chips mount and start growing in the same `flushSync`, and `settle` freezes again at once (`isBusy`), before the `ResizeObserver` reads any height: the ghost has the new chips at full width, so the rows of phase 2 are the final rows and the root animates its height once, in one direction. Before, leavers and enterers were in the DOM together, the ghost held both sets (32 chips, 5 rows), and the root grew past both heights and shrank back (60 → 144 → 88 px for 15 → 17 chips). Surviving chips stay in place during phase 1 and FLIP at the release if the new rows move them. Each chip phase takes half the `duration` (Presence `swap`), so the chips of the whole swap take one `duration`: `settle` sets `hold.swap` when the release mounted waiting chips, and the FLIP of that release runs at `duration / 2` too, in step with the entering chips (a chip animation). The root height is not a chip animation: it starts in phase 2 and takes the full `duration` (see Value Height). The next release clears `hold.swap`.
8. Clearing (or `selectedText` hiding the chips) holds the rows too: the leavers' rows are kept while the title grows at the start of the first row. That row does not overflow: the title is at most the row width (it is truncated, see Trigger Width) and grows while the row's chips shrink, so their sum stays between the two. The title and the chips are not in one `group`, so this holds only as far as their animations start on the same frame. Without the hold, the shrinking leavers would pull each other up row by row.

**Release.** Every chip and title Collapse calls `settle` when it finishes, and so does every chip resize (see Chip Resize). `settle` does nothing until no Collapse animation is running among the `.rac-value` children and no chip label is resizing (`isBusy`: script animations only, not CSS ones, not FLIPs; a delete button inside a chip is not a child, so a hover never delays a release; only during a delete mode hold the delete buttons count, see Delete Mode). It clears the resize floor and the delete mode flags with the held rows. Then it reads the chip positions, replaces the breaks with the resting ones (none, or the reserve rows of Delete Reserve) and drops the leavers in one `flushSync` commit (Presence drops them in the same render; chips waiting for them mount there, see item 7, and a second `flushSync` freezes their rows), and FLIPs every chip that moved: a `transform` animation from the old position, `id: 'rac-flip'`. Rows pulled up after a removal slide into place, and the root height animates by itself (see Value Height).

**Discrete moves at change time.** Some commits move chips at once: a chip inserted in the middle pushes the tail to the next row, a re-added leaver moves to its new place, a controlled `value` reorders. `Snapshot`, a class component in `Value`, records the chip positions in `getSnapshotBeforeUpdate`, which is the only React hook that runs before DOM mutations. After the commit, and after the new breaks are rendered (`breaks` in the layout effect equals the store), every chip that moved is FLIPped from its recorded position. A running FLIP is cancelled first; the recorded position already includes its transform, so a new move starts where the chip is on screen.

**Gotchas.**
- No hold without animations (no `element.animate`, as in jsdom): nothing would ever release it.
- The title is removed from the ghost: it is leaving whenever chips enter (and entering whenever they all leave), at the start of the first row, and its size change offsets theirs.
- A `row-gap` on `.rac-value` shows up once more per break (each break is a flex line of its own and takes a gap): during an animation, and always with inline-on-hover delete buttons. Use `.rac-chip` margins for spacing.
- Touch delete mode opens every delete button at once, inline, and `deleteAlways` / `deleteInline` toggles change every chip's width: those are held too (see Delete Mode).

## Chip Resize

`useChipLayout.js` (the resize effect) + `chipMotion.js` (`snapOf`, `resizesOf`, `resize`) + `chip.jsx` (`Snapshot`): when the chip look changes, every chip animates its size from the old content to the new one, width and height, instead of jumping.

- **Trigger: a mode change only.** `look` is `0` without `valueAsOption`, `1` with it, `2` with it and a `renderOption`, `3` in the pick look (see Plugin Morph). Only a change of `look` animates. A new label text, `texts`, a font or a container change never does (animate on a change of option or state, never on a mere text change). The `renderOption` identity is never read, so an inline function does not trigger anything.
- **What animates: the label, not the slot.** The animated element is the chip's first child, `.rac-chip-text`, `.rac-option-jsx` or the pick-look `.rac-pick` (the element that changed), from its old border box and inline margins to its new ones (`id: 'rac-resize'`, `box-sizing: border-box`, `overflow: hidden`, `text-overflow: clip` and the size limits of both axes lifted, as in Collapse). When the chip's own look changes too (paddings, margins, background, radii: only Plugin Morph does that), the chip animates them and its height in the same run; `isResizing` counts both. The chip and the slot keep their natural size and follow every frame, so an inline delete button that opens during the resize widens the chip as usual. An animated slot width would clip that button and let it pop out at the end.
- **From and to.** `Snapshot` records each slot's position and, on a `look` change, its label's border box (`snapOf`) in `getSnapshotBeforeUpdate`, before the DOM changes. Mid-animation that is the current frame, so a toggle back starts from where the label is and reverses without a jump. After the commit, `resizesOf` cancels running resizes first (all of them, then reads: in a content-sized root one label's size moves the others), reads each new natural box and keeps the labels that changed by more than 0.5 px. A chip whose slot runs a Collapse (entering, leaving, held at 0) is skipped.
- **Hold with a floor.** If anything resizes, `hold.floor` maps each chip id to its old slot width and `freeze` runs: in the ghost, each such slot gets `min-width` = the old width, so the ghost slot is as wide as the wider of the two states. The floor is on the slot, not the label, so a chip box that shrinks while its label grows (Plugin Morph) cannot overflow the held row either. No chip is wider during the resize than in the ghost, so the breaks keep every row; discrete moves (a row split, a re-centred row) are FLIPped by the FLIP effect, which also depends on `look`. `settle` releases the hold when the last resize ends (`isBusy` counts label resizes) and clears the floor.
- **One root animation.** The ghost of a resize hold is laid out at its natural height (`fit`, see Value Height), which is the `.rac-value` height at the end of the resize, and `followHeight` animates the root once to that target.
- **Skipped** under reduced motion, with `duration: 0` and without `element.animate`: the chips change size at once, with no hold.
- **Gotchas.** When the new look needs fewer rows (wide text chips that become narrow rich chips), the old rows are held until the end, so the root first grows with the taller chips and shrinks when the rows merge at the release (two height steps, one FLIP). A chip that is entering or leaving when the look changes takes its new size at once (its Collapse targets the size it measured at its start). A change of the chip's own box through the option's `className` / `style` (padding, border) is not animated, only the content. A container resize during a resize is picked up when it ends (the observer is ignored meanwhile, see Value Height).

## Plugin Morph

`trigger.jsx` (`Value`), `useChipLayout.js` (`entering`, `plain`, the leave loop), `chipMotion.js` (`dressOf`, `resizesOf`, `resize`, `repad`), `chip.jsx` (`SelectedItem` pick look), `chip.css`: in multiple mode, turning the `chips` plugin off or on morphs the chips into the comma-separated picks and back (width, paddings, margins, background, height, comma, rows, root height) instead of remounting with a jump. Found on the playground, where the plugin is a checkbox.

- **The pick look.** With `plain`, `SelectedItem` drops the `rac-chip` class (the chip gets `data-plain`, base: `display: flex`, no shrink, `max-width: inherit`, as a chip) and its label becomes `span.rac-pick` with `data-last`, so the core and consumer rules of `.rac-pick` (margin, comma) apply, and the comma is the label's own `::after`, kerned with the text as in a real pick. The delete button closes, the inline delete reserve is off (its probe still measures, so turning back has the real width), `valueAsOption` content gives way to the text label. `look` becomes `3`, so the switch is a Chip Resize: rows held with the slot floor, label and chip box animated, FLIP, one root animation to the ghost height.
- **Out (plugin removed).** `Value` keeps rendering the old slot with `leaving` until it calls `onLeft`; the slot shows the pick look, then a loop (one `requestAnimationFrame` per frame) waits until the hold is released and no finite animation runs in `.rac-value`, and calls `onLeft`. `Value` then renders `Picks`, which mounts without animating (Presence `appear` off). The pick look matches the real picks to the pixel (measured: every label box equal to 0.01 px in Chromium and Firefox), so the swap is invisible.
- **In (plugin added).** `Value` passes `enter` (the slot replaces `Picks` of a multiple Select); the slot mounts in the pick look, identical to the picks it replaces, and leaves it one frame later, which plays the resize to chips. `enter` is read once, at mount.
- **Comma.** Leaving, the comma appears with the pick look and fades in (`::after` opacity) while the label grows by its width. Entering, the chip label has no comma, so the old one is kept as a transient `data-sep` + `--rac-sep` (base rule `[data-sep]::after {content: var(--rac-sep)}`) and fades out while the label shrinks; the label animations hold their end size (`fill: forwards`) until `done` removes the comma, because a `settle` from another event (a delete button `onEntered`) can run before the animations' own `finish` and would otherwise measure the rows with the comma back at full width (measured: a 73 px row jump at the release).
- **Value padding.** The picks' block padding (Picks, Rows) switches with the pick look, so `repad` animates `.rac-value` `padding-block` in the same run; otherwise the first row jumped down by about 7 px. `.rac-value` is `border-box` in both looks: with `content-box` the chips' `min-height` added the padding still running, and a single row grew by 14 px for a frame on entering (found on video; two rows were taller than `min-height`, so they hid it).
- **Root height.** One memo (`Value`'s `height`) serves both branches, so the new branch animates from the old height instead of recording it. `followHeight` starts from the running animation only while it is really running: the release of a hold can come in the same frame as the end of the root animation, before its `finish` event, and the old check (`memo.anim` set) read the new natural height as the start and jumped (measured: 72 → 54 px in one frame with `deleteAlways`).
- **Background.** The theme's `background-color` transition on `.rac-chip` starts when the class comes back, so the end look was measured at its first frame (transparent) and the background popped in after the resize (found on video). `resizesOf` finishes the chip's CSS transitions before it measures the end look; the WAAPI animation then owns the change.
- **Skipped** (an instant swap): `duration: 0`, reduced motion, no `element.animate`, no chips (placeholder or `selectedText`), and `multiple` turned off (single mode never morphs).
- **Measured** (300 px Select, 9 chips, `duration` 600, Chromium and Firefox; off, on, and reversed mid-way both ways; plain, `deleteAlways`, `deleteInline`, `valueAsOption` with a rich `renderOption`, a label wider than the row): no element moves more than 1.8 px per frame except along FLIP curves (smooth, peak 12.7 px), the root height steps at most 3 px per frame, no console errors.
- **Gotchas.** Turning off needs fewer rows, so (as in Chip Resize) the chips shrink in their old rows and the rows merge at the end: the swap happens after `duration` + the FLIP, about 1.25 s at 600 ms. A consumer border on `.rac-chip` disappears at once (a border style cannot animate). A chip that is entering or leaving when the plugin toggles takes its new look at once.

## Delete Reserve

`useChipLayout.js` + `chipGeometry.js` + `chip.jsx` + `motion.jsx`: with `deleteInline` (and no `deleteAlways`), hovering (or swiping) a chip opens its delete button inside the chip, and the chips after it on its row slide right to make room. Nothing ever changes rows, and the Select never changes height.

- **Reserve by layout, not by an element.** Every row is laid out as if `.rac-value` were narrower by the button width D: `ghostRows` gives the ghost an extra end padding of D, with the delete buttons removed from it. A padding, not a smaller width: a Select sized by its content grows by D for the ghost, so a single row that fits stays single (see Trigger Width). The row ends found there become breaks, the same `rac-spacer` breaks as in Chip Hold, but kept at rest too (`restBreaks`). Each row therefore always has D of free space at its end, enough for one open button.
- **No feedback loop.** The ghost drops every break and every button before it measures, so the rows depend only on the chips' own widths and the Select's width, never on the breaks or buttons already on screen. The old element-based spacer (`rac-del-spacer`, a min-width D inside the row-end chip's slot) changed the very layout that decided where it went. It could push its chip to the next row, move to the previous chip, and end up between the last two chips of a row. Its mount animation always lasted 300 ms, whatever the `duration`.
- **One open button per row.** Hover and swipe are single ids, so at most one button is targeted open. The buttons share a `Collapse` `group` (see Collapse Group), so while buttons hand over, their widths in a row add up to at most D in every frame. The old design shrank the spacer with a CSS transition and grew the button with WAAPI. The two reverse differently when interrupted and start about a frame apart, and chaotic hovering overflowed the row.
- **Rounding slack.** The ghost is `SLACK` (0.25 px) narrower still, because Firefox's per-button rounding can push a handover a few app units past D (see Collapse Group). 0.25 px is 15 app units, and each member adds at most half of one. A row filled to within 0.25 px of the limit therefore breaks one chip earlier, which is invisible and stays stable. Without the slack, such a row wrapped its last chip for a frame now and then, and the root started a height animation. A consumer border on `.rac-chip-del` may not be covered: Firefox snaps thin borders to whole device pixels, which can exceed the slack mid-animation.
- **Measured from the real button.** D is the full box (width plus margins) of a hidden `button.rac-chip-del` probe with the real `icons.remove`, rendered once inside `.rac-value`, so consumer padding, borders and margins on `.rac-chip-del` count. The old probe measured only the icon. The probe is rendered only once there is a chip, so a Select without chips measures nothing on mount; the first chip's commit measures it and re-runs the layout before paint.
- **Inside a hold.** The held rows are measured at `width − D` as well, so hovering stays safe while chips enter or leave, and a chip removed through its own open button (its slot starts as chip + D) still fits its row. A delete mode hold of the widest chips ignores D (every button is already in its rows, see Delete Mode).
- **When.** The reserve applies with `deleteInline`, without `deleteAlways`, with an `icons.remove`, outside touch delete mode (there, and with `deleteAlways`, every button is already open and nothing changes on hover). Overlay mode (the default) needs none: its buttons are absolutely positioned.
- **Gotchas.** A chip wider than the row minus D truncates its text further while its button is open. In a Select sized by its content, the root widens by D while a button is open, since nothing reserves that width at rest. Chip width changes that resize nothing and are not a font swap (a consumer restyling `.rac-chip` at runtime) are picked up at the next chip change.

## Delete Mode

`useChipLayout.js` (the `dress` effect) + `chipMotion.js` (`shift`, `isBusy`) + `chipGeometry.js` (`snapRows`, `ghostRows`) + `chip.jsx` (`Snapshot`, the button's `settle`): a change of how the delete buttons are dressed animates the chip widths, and no chip changes rows in the middle of it. Covers `deleteAlways` and `deleteInline` toggles and entering or leaving touch delete mode.

- **Dress, a mode like `look`.** Two bits, only with `icons.remove`: the button is in the flow (`deleteInline` or delete mode) and it is always open (`deleteAlways` or delete mode). Only a change of these bits animates. `Snapshot` records the chip positions on that change, so the discrete moves are FLIPped by the FLIP effect, which also depends on the dress.
- **Why it jumped.** `deleteAlways` true → false with `deleteInline`: the buttons closed over `duration` while, in the same commit, the reserve appeared and the resting breaks were measured for the narrow chips; the live chips were still wide, the last chip of a row wrapped, a third row showed for some frames (root 132 → 150 → 100 px measured). `deleteInline`: `.rac-chip-del` switched between `position: absolute` and in-flow in one frame, so every chip width jumped by the button width (a 16 px step), and the rows and the root followed. Delete mode had both problems.
- **Width.** An open/close of the buttons is their own `Collapse` (in the flow when inline). An in-flow ↔ overlay switch is a `rac-dress` animation on every open button (`shift`): `position: relative` in both frames, and the margins and height that put an in-flow button exactly where the overlay is: the start margin moves it back over the end of the label, the end margin cancels its width, the block margins and the height match the overlay box. Both boxes are measured before paint in the layout effect (the other placement by an inline `position`, set and removed in the same read), relative to the chip and in logical directions (RTL works). When the animation ends, CSS takes over at the same geometry, so nothing moves. The chip's real width changes every frame; the background of the button follows through its CSS transition. A button that is closing while it leaves the flow (leaving delete mode in overlay mode) gets only `position: relative` until the end, so its Collapse still shrinks the chip. An interrupted switch starts from the current frame, computed from the frames and the progress (as in Collapse Group).
- **Hold.** When a dress change has any button animating and the flow bit is set in one of the two states, the rows are held (`hold.dress`). First choice: the current rows (from the `Snapshot`, layout positions, no transforms), kept if the ghost of the end state (end chips, the new reserve) does not split them. Second choice (`hold.wide`): the ghost keeps every delete button, forced into the flow at full width, and ignores the reserve: the rows of the widest chips. Why the first choice: chip widths and the row width (the clear button and the arrow, hidden in delete mode) move on the same clock, so rows that fit both end states fit every frame; leaving delete mode held an extra row with the widest chips at the narrower row (100 → 132 → 100 px). A reserve measured a commit later (the probe on the first switch to inline-on-hover) re-freezes by the same rules.
- **Release.** The delete buttons call `settle` on `onEntered` / `onExited` and the `rac-dress` animations on finish. While `hold.dress` is set, `isBusy` counts every script animation on `.rac-chip-del`; outside it a hover still never delays a release. At the release the flags clear, the resting breaks apply (the reserve rows of Delete Reserve), moved chips FLIP and the root height follows (see Value Height).
- **Height.** Narrow → wide: the rows change at the start and the root animates once with the chips. Wide → narrow: the rows merge at the release, so the chips shrink first and then the rows move and the height follows: two steps, the limit accepted for Chip Resize too. An interrupted toggle (narrow → wide → narrow) grows to the wider state, then shrinks at the release; it never goes above the larger end state.
- **Skipped** under reduced motion, with `duration: 0` and without `element.animate`: the change is instant, with no hold.
- **Gotchas.** A button whose Collapse is running when its placement switches (a hover opening or closing at that moment) gets no margin animation: leaving the flow it stays in the flow until the end and then takes the overlay place in one frame; entering the flow it joins at once. A Collapse that starts on a button during a `rac-dress` animation (a hover, or `deleteAlways` toggled mid-way) overrides its margins (both animate the inline margins; the later one wins) until one ends: a small offset of that button for the rest of the animation. Vertical writing modes are not handled (`top` is used for the block axis).

## Paging

`paging.jsx` (the `paging` plugin) + its seams in `useSelect.js`, `useSelectModel.js`, `model.js`, `dropdown.jsx`. Since 0.8 `hasMore`, `loadMore`, `loadButton`, `loadOffset` and `loadAhead` need `plugins={[paging]}`; without it they do nothing and warn once (`no paging`, see Dev Warnings).

- `request({props, lock, setPending})` (pure seam, called by the core `loadMoreOnce`): the `hasMore` and lock checks, the `no loadMore` warning (`hasMore` without `loadMore` warns once and loads nothing), `setPending(true)`, `loadMore()` with settle on resolve or reject, and the sync throw (unlock, settle, `reportError`). `setPending` dispatches `{loadPending}`; the raw `setState` never crosses the seam.
- `row({hasMore, loadButton, loadPending, moreText, pendingText})` (pure seam, called in a `useMemo` of `useSelectModel.js`): the "Load more" record or `null`; `normalizeOptions` appends it as `tail`. Row contract, read by the core: `{id: 'special-load-more-id', name, loadMore: true, loading, type: 'special'}`. `selectOption` reads `loadMore` / `loading`, `useReachable` skips `loading` while the highlight effect keeps an index on a `loadMore` row (see Highlight, Load row kept), `OptionItem` draws `data-loading` / `aria-disabled` / dots, and the live region counts only records with `original`. The texts are passed as strings: `texts` is a new object every render and would rebuild the model.
- `PagingFooter` (the `Footer` slot of `Dropdown`) renders the core `StatusRow` with `more` (the loading-more row in scroll mode, `!loadButton && hasMore`) and a `ref`. In scroll mode a row always exists (error, loading or loading-more), so its `parentElement` is `.rac-list`. Load-ahead: `near` is read from `highlightStore` with `useSyncExternalStore`: the effective highlight index while it is within `loadAhead` of the end, otherwise `null` (not a boolean: every move inside the zone must re-check, so a load that failed is retried on the next key, as before 0.8). A layout effect on `near`, `visibility` and the option count calls `loadMoreOnce`; the footer re-renders only while the highlight moves inside the zone.
- **Infinite scroll** (`IntersectionObserver`, since 2026-10-04). While `!loadButton && hasMore && visibility`, the status row is observed with `root` = `.rac-list`, `threshold: [0, 1]` and a bottom `rootMargin` of `loadOffset` minus the list's `padding-bottom` (read once per observer). The row counts as near when its **bottom** edge is inside `rootBounds` (the rects come with the entry): that is the old `scrollHeight - scrollTop - clientHeight <= loadOffset` exactly, while `isIntersecting` alone fired one row height early. Becoming near calls `loadMoreOnce`. No layout is read on scroll. A passive `scroll` listener stays only to retry: while the row is near, it re-checks the old exact geometry (`scrollHeight - scrollTop <= clientHeight + loadOffset`) and calls `loadMoreOnce`, so after a failed load any scroll near the end retries, as before. Away from the end it reads nothing. The re-check matters: a scroll event is delivered before the observer callback of the same frame, so a fast scroll away would otherwise act on a stale `near` and send one request the user did not ask for. With `error` on, the row stays and both still fire.
- Why: the old listener read `scrollHeight` / `scrollTop` / `clientHeight` on every scroll event, and it could never fire when the first page did not fill the list (nothing to scroll): the list stayed short until a key press. Now a short list loads by itself, page after page, until it fills or `hasMore` turns off. That is a behaviour change of 0.8.
- **Re-arm, not re-check.** An observer reports only changes: a page that lands while the row stays in the zone sends nothing. `armed` latches the option count while nothing is pending (adjust-in-render state); when it changes, the effect re-creates the observer, whose first callback reports the current state. Only a page that added options re-arms; a failed load (count unchanged) does not, so a `loadMore` that always fails is called once, not in a loop. The callback is asynchronous, so it runs after the core's passive effect has opened the lock (the footer's effects run before its ancestors').
- **One node.** `StatusRow` renders the error, loading and loading-more states as one `div` (attributes and text change), so the observed node never swaps; a swap would leave the observer on a detached node, and `error` turning on would re-arm into an instant retry.
- Not observed while closed (`visibility`), so a `keepMounted` panel loads nothing. `loadOffset` goes through `Number()` (a numeric string works); a non-finite value is treated as `0` (`rootMargin` throws on `NaN`). Gotcha: a row that can never be fully inside the zone (taller than the list plus `loadOffset`, or clipped sideways by consumer CSS) never counts as near, so scroll loading stops there; the keyboard and the button still load. Without `IntersectionObserver` (jsdom) scroll loading is off; the keyboard and the button still load.
- Stays in the core (generic, small): the `loadPending` field (`aria-busy`, the row's `loading`), `loadLock` and its two release effects, `selectOption`'s `loadMore` branch, `noWrap` in the keyboard `step`, the live region's `loaded` text, and the props' defaults.
- Gotcha: a page that lands while the keyboard highlight stays near the end does not chain the next load through load-ahead (the lock opens in a passive effect after the re-check); the next highlight move does. In scroll mode the re-armed observer chains it when the row is still in the zone.

## Options Panel

`dropdown.jsx`, `Dropdown`: the dropdown panel. It is a `position: absolute` portal into `document.body` (or `container`), a `Collapse` on the y axis (with `fade` when `animateOpacity`). Inside it are the `role='listbox'` element (with `id` `${selectId}-listbox` and `aria-multiselectable` when `multiple`), the `OptionList`, and the footer: the `paging` plugin's `Footer` slot when present, otherwise the core `StatusRow` (the error row, or the loading row while `loading`). `Dropdown` owns `panelRef`, which is passed to Collapse as `nodeRef`, and it positions itself (see Dropdown Position).

- The custom properties (`--*` keys) of the Select's `style` prop are copied onto the panel; other keys stay on the trigger. Because the panel lives outside the trigger's DOM, this lets a consumer theme the list from one place (`style={{'--rac-bg': …}}`). `--rac-duration` and `--rac-ease` (from `duration` and `easing`) are applied after them, as on the trigger.
- `.rac-options` is `overflow: clip` (base). Collapse frames clip it while it opens; without the same clip at rest, a consumer `border-radius` held during the animation and broke when it ended: the list background, its scrollbar and a highlighted first or last option drew square corners over the rounded border. `clip`, not `hidden`: the panel never becomes a scroll container, so `scrollIntoView` of an option scrolls only the list.
- Only `position: absolute` and `pointer-events` are inline from React (the panel's mechanics; `none` while closing, so the collapsing panel catches no clicks). The position hook writes the geometry and `--rac-visible` straight onto the element (see Dropdown Position); the opacity itself stays in `.rac-options`. `z-index` and `box-sizing` live in `.rac-options`, where a consumer can change them.
- The panel carries `data-placement='top'|'bottom'` (written by the position hook), the same value as the trigger, so a consumer can style it by side (corners, shadow, `transform-origin` for their own effects).
- The status row at the end of the list: with `error`, `.rac-option[data-error]` with `texts.error`; otherwise, with `loading` or in auto-loading mode, the loading footer `.rac-option[data-loading]` with `texts.loading` or `texts.loadingMore` and the shared `dots` (see State Semantics). The listbox is labelled by `texts.list`.
- The closed panel unmounts after its exit animation; `keepMounted` keeps it in the DOM, collapsed. Switched on while the Select is closed, it renders the panel collapsed at once (see Collapse, Mount rules).
- `container` (`portalTarget`): an element, or a function returning one (called on every render of the panel), else `document.body`. Needed inside modals and focus traps (Radix, MUI, Headless UI), which treat a click in `document.body` outside their content as an outside click and close. A function returning a still-empty ref falls back to `document.body` until the next render; a callback ref kept in state is the reliable form.
- `onEntered` calls `setListReady(true)`, so the list is marked ready only after the open animation has really finished.
- `Dropdown` is `memo` with no props, and `Select` renders it next to `Trigger`, so it re-renders only through its contexts.

## Dropdown Position

`dropdownPosition.js`, `useDropdownPosition` (used only by `Dropdown` in `dropdown.jsx`): the one source of truth for where the panel goes.

- **Direction while closed.** It is estimated from the last known list height H (or `--rac-list-max-height`, default 250px), so the trigger arrow already points the right way before opening. The rule: up when the list does not fit below (`innerHeight - bottom < H`) and there is more room above (`top > innerHeight - bottom`). Two `IntersectionObserver`s fire exactly where each half of the rule flips: one with `rootMargin: 0 0 -H 0` (thresholds `0, 1`: the trigger bottom crosses the line H above the viewport bottom), one with `rootMargin: 0 0 -50% 0` (thresholds `0, 0.5, 1`: its centre crosses the viewport middle). The direction is computed from the geometry in the entries, which the browser has already computed: no layout read, no scroll listener, callbacks only around a flip. It is set up in `useEffect`, after paint, so mounting many Selects reads nothing during the commit.
- **No React render.** `data-placement` is written straight onto the trigger and the panel (`mark`, only when it changes); neither element renders it, so React never overwrites it. Before the first observer callback (and in SSR HTML) the attribute is missing, and `base.css` treats a missing value as `bottom`. Gotcha: a Select that mounts near the bottom of the viewport paints its arrow down for one frame, then rotates.
- `--rac-list-max-height` is registered with `@property` as a `<length>` (in `base.css`), so its computed value is always in px and any unit (`20em`, `50vh`) is read right. An invalid value falls back to the initial 250px. Without `@property` support, only px values are read correctly.
- **While open, document coordinates.** `place` writes `width`, `left` and `top` / `bottom` straight onto the panel, which is `position: absolute` in document coordinates (`rect + scrollX / scrollY`): `left` is `rect.left + scrollX`, `top` is `rect.bottom + scrollY + offset`, upward `bottom` is `innerHeight - rect.top - scrollY + offset` (the trigger edge pinned to its visible part, see Clipped trigger). Page scrolling therefore moves the trigger and the panel together on the compositor thread; a `fixed` panel re-placed from `scroll` events trailed the trigger on phones by a frame or more.
- **Following the trigger.** `key()` is the trigger relative to the panel (left offset, the gap between the trigger's visible edge and the panel on the open side, the visible fraction, width, viewport height, list height, direction). A `requestAnimationFrame` loop re-places while the key changes and stops after two still frames. It is started by a capturing scroll listener (nested scroll containers, a `fixed` container), `resize`, a `ResizeObserver` on the trigger and the panel, a `MutationObserver` on `document.body` (any DOM change outside the Select and its panel, checked in the microtask, so an instant layout jump is fixed before paint) and a layout-shift `IntersectionObserver` (`arm`: its root is the trigger box itself with `threshold: 1`, so any move of the trigger drops the ratio below 1). Page scroll does not change the key, so it writes nothing. Measured in the sandbox: the gap is exact in every frame for animated and instant layout changes above and below, page scroll and nested scroll.
- **Following through the close.** `Dropdown` keeps `following` true from the open until its Collapse reports `onExited`, so the loop and the observers keep the closing panel at the trigger: a layout change or a scroll during the exit no longer leaves the collapsing panel where it started. While closing (`frozen`) `place` keeps the current side, so the panel never jumps to the other side mid-exit. The closed-state observers start only after the exit.
- **Clipped trigger (pin + fade).** `clipsOf` collects the trigger's clipping ancestors once per open (`overflow-y` other than `visible`, up to `body`; lazily, in the first `place` of the open). `visible` intersects their padding boxes into the visible window of the trigger: `pin` clamps a y into it, `ratio` is the visible fraction of the trigger's height. Their rects are read only by `place` and `key()`, so only while the loop runs, and not at all without such ancestors.
  - Pin: the panel's open edge attaches to the trigger's visible edge, `pin(rect.bottom)` downward, `pin(rect.top)` upward. While a container clips the part of the trigger next to the panel (the panel opens down and the trigger slides under the container's bottom edge), the panel hangs at the container edge: the hidden part of the trigger no longer leaves a gap between its visible part and the options. Horizontally the panel keeps the full trigger width and left.
  - Fade: below 1, `ratio` is written onto the panel as `--rac-visible` (removed at 1), and base derives `.rac-options {opacity: var(--rac-visible, 1)}`. A variable, not an inline `opacity`: a consumer's own `opacity` on `.rac-options` wins over it (then write `calc(var(--rac-visible, 1) * x)` to keep the fade). There is no opacity transition at rest, so the opacity follows the scroll frame by frame.
  - At `ratio` 0 the panel gets `data-offscreen`: base runs the `opacity` transition over `--rac-duration` only on this rule and sets `visibility: hidden` after it, so a hidden panel catches no clicks and a jump scroll that hides the trigger at once still fades the panel out. Leaving `data-offscreen` has no transition: a trigger that comes back at once shows its panel at once.
  - The Collapse `fade` (WAAPI) overrides the CSS opacity while it runs; it reads the computed opacity at the start, so a panel opened half clipped fades in to the visible fraction. `listRef` places the panel before that read (see Placed before it is measured).
  - The panel stays open, so the keyboard keeps working. A trigger that leaves the viewport itself keeps its panel, which scrolls away with it; the viewport and `body` / `html` are not clip ancestors. An app shell that scrolls in a full-height `div` is one, so there the panel fades with the trigger at the shell's edge.
- Limits: a nested scroll container scrolls on the compositor too, so there the panel still follows from the main thread (a frame late on fast touch scrolls). Only vertical clipping pins and fades; a trigger clipped sideways keeps its full-width panel. Clip ancestors are found by `overflow-y` alone: an ancestor that does not really clip the trigger (outside its containing-block chain, for an absolute or fixed trigger) still counts, and `contain: paint` or `clip-path` do not. The list is not refreshed while open. The layout-shift observer is not armed while the trigger is partly outside the viewport; the scroll listener and the loop still cover it.
- **Placed before it is measured.** The listbox has a callback ref (`listRef`) that places its parent, the panel. React attaches refs child-first in the layout phase, so this runs before the layout effect of the panel's `Collapse`, which measures the open height. Placed only in `useDropdownPosition`'s own layout effect (a parent effect, so after Collapse's), the fresh panel was measured at its shrink-to-fit width: with long wrapping options the open animation ran to a wrong height and snapped at the end. `listRef` changes with `open` and places only while open, so a `keepMounted` panel is placed again on every open (before its Collapse reads its opacity) and not while it mounts closed.
- **Containing block.** An ancestor that is positioned, or has a `transform`, `filter` or `contain` (a modal body centered with `translate(-50%, -50%)`, set as `container`), becomes the containing block of the `absolute` panel, so the page coordinates no longer match. `shift` reads where the panel really landed (minus its margins) and corrects `left` and `top` / `bottom` by the difference, so the panel sits at the trigger in any container. Every side is corrected relative to the value `place` wrote (page coordinates), never rebuilt from the trigger rect (viewport coordinates): rebuilt, `left` lost `scrollX`, and on a page scrolled sideways the panel sat that far left of the trigger. A scaled container is not compensated.
- Without `ResizeObserver` / `IntersectionObserver` / `MutationObserver` (jsdom in consumer tests) the observers are skipped; the scroll and resize listeners still work, and the closed direction stays `bottom`.
- Why not a store: the old `positionStore` re-rendered `Trigger` and the closed `Dropdown` on every flip only to change one attribute, and its closed-state observer used visibility thresholds, so a fully visible Select never updated while the page scrolled. The hook lives in its own `.js` file because the Fast Refresh lint rule forbids exporting a hook next to a component, and `dropdown.jsx` with it passed the file limit.

## Dropdown Flip

`dropdownPosition.js` (`place`, `replace`) + `dropdown.jsx` (`flip`): how an open panel changes sides.

- **Hysteresis.** A fresh panel (no `data-placement`) takes the side from the rule in Dropdown Position. Once placed, it keeps its side while the list still fits there (`H + offset` of room) and while a scroll container clips the trigger (`ratio < 1`, see Dropdown Position, Clipped trigger); only then the rule decides again, so a half-hidden trigger never flips its panel toward the visible part. Without it, the side flipped whenever the trigger's centre crossed the viewport middle while the list did not fit below, so scrolling an open Select made the panel jump between sides. `key()` carries the fit of both sides, so a change of either re-runs `place`.
- **Animated flip.** When `place` would change the side of an open panel, it keeps the current side and calls `onFlip`. `Dropdown` then runs `flip = 'out'`: the Collapse closes on the old side (`in` false, side frozen, `aria-expanded` stays `true`, the panel stays mounted). On `onExited` it calls `replace` (drops `data-placement`, places afresh on the new side) and sets `flip = 'in'`: the Collapse opens there. `onEntered` clears `flip`. Both halves run at `duration / 2`, so a flip takes one `duration`, like an open.
- A close during the flip ends it: `onExited` with `open` false clears `flip` and stops following, and the panel unmounts as usual. A second flip request during a flip is ignored.
- The open effect's cleanup drops the panel's `data-placement`, so a `keepMounted` panel decides its side afresh on the next open instead of starting a flip.

## Server Render

The Select must render to HTML on the server (Next.js, Remix, `renderToString`) and then hydrate on the client without a mismatch.

- Every output file starts with `'use client'` (a Rollup `banner` in `vite.config.js`, see Package Build), so a Next.js server component can import the Select. `defineOption` components still have to be declared in a client module.
- `Dropdown` reads a `client` flag through `useSyncExternalStore(noSubscribe, () => true, () => false)`. On the server and during hydration it is `false`, so the portal (`document.body`) is not rendered. In a client-only app (`createRoot`) React never calls the server snapshot, so the flag is `true` on the first render: no extra render and no delay there.
- After hydration React re-renders `Dropdown` once with `true`, and the panel mounts. The server HTML never contains the panel, even when `open` starts `true`; the trigger itself is complete in the HTML.
- `useDropdownPosition` gets `open: visibility && client`, so its layout effect re-runs when the panel appears and positions it. Without that, a panel that is open at hydration would stay unpositioned.
- The whole option model (array `options` and JSX options alike) is built during render, so the server HTML already has the right title, chips and enabled state. Nothing switches after hydration.
- DOM ids come from `useId` and from option paths (see Dom Ids, JSX Options), so the server and the client produce the same ids and ARIA references.

## Option List

`optionList.jsx`: `OptionList`, `OptionItem`, `GroupHeader`.

- `OptionList` builds the list structure from `normalizedOptions`: plain options, group headers, and one collapsible `Collapse` container per group. The result is memoized on the model, the selection, `expandedGroups` and `multiple`.
- The highlight is not an input of `OptionList`. Every `OptionItem` subscribes to `highlightStore` with a selector that returns one of three modes (none, highlighted, highlighted and ready), so a highlight change re-renders only the two affected options.
- `OptionItem` and `GroupHeader` are `memo`, and their props are primitives or model objects that keep their identity (see Option Model).
- Row content (`optionContent`, see Option Content): the option's own JSX (`<Option>` children) wins. Otherwise, with `renderOption`, a row that comes from real data (`'original' in option`: array items and JSX options, not the load-more row or empty/invalid placeholders) renders `renderOption(original, {selected, disabled})` inside `.rac-option-jsx`. Otherwise the text `name` in `.rac-option-text`.
- Checkbox (`.rac-check`, multiple mode): only on rows that can be selected, so not on disabled options and not on records without `original` (the load-more row, placeholders). Group headers are `GroupHeader` and never have one.
- Row states are attributes, not classes (see State Attributes): `aria-selected`, `aria-disabled`, `data-highlighted`, `data-invalid`, `data-loading`, `data-bool`. `data-invalid` comes only from the model's `invalid` flag (a function in `options`), never from comparing the row text with `texts.invalidOption`. The checkbox (`.rac-check`, `data-default` without a custom `icons.checkbox`) shows its `.rac-checkmark` (`icons.check`) from the row's `aria-selected` (opacity and scale; the mark is absolutely centered over the frame or the custom checkbox icon).
- No `:hover` rule on rows: `mouseenter` sets the highlight, so pointer and keyboard share `data-highlighted`. A selected row that is highlighted has its own, stronger color, so the keyboard position stays visible on selected rows. A group header is `.rac-group` with `data-open` / `data-disabled` / `data-highlighted`; its arrow is the `.rac-group-arrow` Collapse itself.
- `useHighlighted(index)` is the one highlight subscription, shared by `OptionItem` and `GroupHeader`: a mode selector (none, highlighted, highlighted and ready) and the scroll into view once ready.
- Groups in ARIA: a group header is `role='option'` with `aria-selected='false'`, because the keyboard path reaches it and `aria-activedescendant` must point at an option. Its accessible name carries the state: `aria-label` is `<name>, <texts.groupOpen | texts.groupClosed>` ("Engineering, collapsed"). A disabled or empty header has `aria-disabled` and only its name: it cannot be toggled. `aria-expanded` is not used, because ARIA 1.2 does not allow it on `option`. The `.rac-group-items` container is `role='group'`, and its `aria-labelledby` points at the header's inner `.rac-group-text` (`groupLabelId`), not at the header itself, so the group name carries no state. `data-open` stays for styling. A collapsed group's container is unmounted, so it is not in the tree.

## State Attributes

States are exposed as attributes on the element that has them, never as modifier classes. The one rule: an ARIA attribute where it is semantically exact, a valueless `data-*` flag (`flag()` in `utils.jsx`: `''` or absent) for the rest.

- Root: `aria-expanded`, `aria-disabled` (disabled or no options), `aria-busy` (loading or a pending `loadMore`), `data-error`, `data-empty` (no value), `data-deleting` (touch delete mode), `data-inline-delete` (`deleteInline`), `data-placement='top'|'bottom'` (panel side, also on `.rac-options`).
- The trigger reacts to hover only while interactive (not with `aria-disabled`); with `data-error` the hover keeps the red border. Cursors: `progress` while busy, `not-allowed` while inactive, `wait` while both.
- Why: the attributes are needed anyway for ARIA, a consumer styles open and error states with plain selectors (`.rac-select[aria-expanded='true']`), and the markup carries no `--open`/`--up` modifier pairs.
- Arrow: rotated `180deg` exactly when closed with the panel below, or open with the panel above. That is one CSS rule on `aria-expanded` and `data-placement`, so a custom `icons.arrow` needs no class.
- The full table is in the package's `STYLES.md` (`packages/react-animated-select/STYLES.md`).

## Styles Layer

`base.css` + `theme.css`, both imported by `select.jsx`, and `chip.css`, imported by `chip.jsx` (the `chips` plugin). Everything is inside `@layer rac`, split into two sublayers declared in this order at the top of every file: `@layer rac.base, rac.theme;`.

- A plugin's CSS lives in its own file with both sublayers, so it ships only with the plugin and its layer order is right whichever file loads first. The core CSS is imported by `select.jsx`, not `index.js`: the package is `"sideEffects": ["**/*.css"]`, and Rollup, rolldown and webpack keep a side-effect-free module's CSS only while a binding of that module is used. `index.js` only re-exports, so its CSS imports were dropped for a consumer importing `{Select}` alone (measured: an unstyled Select in rolldown-vite and webpack); `select.jsx` is always used. Those bundlers drop `chip.css` with an unused `chips`. esbuild keeps every CSS file reachable from JS by design (since 0.17.7, `sideEffects` is ignored for CSS), so an esbuild consumer gets `chip.css` even without `chips`; only a subpath entry would avoid it, and the package keeps one import point. `index.js` re-exports `select.jsx` before importing a plugin, so the core CSS comes first in dev. The plugin rules never share a selector with core rules (a shared list like `.rac-clear, .rac-chip-del` is split), so their order inside a sublayer does not matter.

- Any unlayered consumer CSS beats the library regardless of specificity, so overrides need no `!important` and no selector copying. A consumer using their own layers must declare `rac` first (`@layer rac, app;`); the sublayers stay inside it.
- **`rac.base`** (`base.css`) is what the Select needs to work: the flex layout of the trigger and the value area, `--rac-row`, button resets, the arrow and group arrow rotation, the loading dots, the chip mechanics (touch, the overlay or inline delete button, the `rac-spacer` breaks; in `chip.css`), the panel's `z-index` and scrolling, the checkbox frame and the checkmark reveal, cursors per state, icon image size, reduced motion. Motion that shows a state (arrow rotation, checkmark reveal) is base, because the animation is the product.
- **`rac.theme`** (`theme.css`) is the default look: colors, borders, padding, margins, typography, color transitions, the delete mode shake (the chip look and `rac-shake` in `chip.css`). Themes and presets are the consumer's choice; the theme is kept neutral and small.
- Tokens: the inputs `--rac-bg`, `--rac-fg`, `--rac-danger`, `--rac-success`, `--rac-radius` (see Corner Radius) are on `:root`. The derived tints (`--rac-tint-1..3`: 5, 10, 20% of `fg` over `bg`) and `--rac-muted` are declared on `.rac-select` and `.rac-options`, not on `:root`: a derived variable resolves where it is declared, so on `:root` it would ignore a `--rac-fg` set on one Select. Setting `--rac-fg` or `--rac-bg` on a Select (class or `style`) retints its trigger and, through `style`, its panel.
- Variables exist only for values shared by several rules, values read by JS (`--rac-list-max-height`), values written by JS (`--rac-visible`, the visible fraction of a clipped trigger, inline on the panel; see Dropdown Position) and values fed from props (`--rac-duration`, `--rac-ease`, inline on the root and the panel). Everything else is a plain property under its class.
- `duration` and `easing` drive every animation: Collapse and the chip FLIP and height animations read them from the config, CSS transitions read `--rac-duration` / `--rac-duration-fast` and `--rac-ease`. `--rac-duration-fast` is derived on `.rac-select` and `.rac-options` for the same reason as the tints. The looping indicators (`rac-blink`, `rac-shake`, `rac-busy`) keep their own period: they are not transitions.
- Reduced motion: `--rac-duration: 1ms !important` under `prefers-reduced-motion` (an important declaration beats the normal inline style that carries the `duration` prop), and the dots and the shake stop; the busy stripe becomes a static line.
- Keyframes are prefixed (`rac-blink`, `rac-shake`, `rac-busy`) so they cannot collide with the page's own.
- `renderOption` is a config prop: a new function identity re-renders every config reader (trigger, chips, rows). Consumers with large lists should pass a stable function (`useCallback` or module scope). It affects list rows, and the title and chips only with `valueAsOption` (see Option Content).

## Corner Radius

`theme.css`: `--rac-radius` (`0px` on `:root`) is the one corner radius of the theme. `.rac-select` and `.rac-options` use it, `.rac-chip` uses half of it, and `.rac-chip-del` inherits its two end corners from the chip.

- Why a variable: the radius is shared by several rules (trigger, panel, chips), and a theme rounds them together. One line (`:root {--rac-radius: 8px}`, or `style={{'--rac-radius': '8px'}}` for one Select and its panel) replaces a rule per element. The panel border stays a plain property: one rule uses it (decision 2026-10-03; recipe in STYLES.md).
- The list needs no radius of its own: `.rac-options` clips (see Options Panel), so the list, its scrollbar and a highlighted first or last row follow the panel's corners.
- The delete button: the overlay sits at the chip's inline end with its own background, so on a rounded chip its square corners stuck out (also with the old "pill chips" recipe). Inheriting the end corners (logical, so RTL works) makes it follow any chip radius, the variable's or a consumer's `.rac-chip {border-radius}`. Its start corners stay square: they lie inside the chip. Inline and in delete mode it is transparent, so the corners do not show.
- The default is `0px`, not `0`: the chips compute `calc(var(--rac-radius) / 2)`, where a unitless `0` is a number, not a length, so the declaration is invalid at computed time (it still ends at `0`, the initial value). Any non-zero consumer value needs a unit anyway.
- A portal panel does not see an ancestor's variable: set it on `:root`, the `container`, or through `style` (copied onto the panel), like the colors.
- No radius transition in the theme (decision 2026-10-03): the library animates the Select's states, and a radius is a theme value that changes only when the page switches themes, which is the page's call. The STYLES.md recipe adds it with one `transition-property` line: the theme's duration and easing lists repeat over the longer property list, so the trigger keeps `--rac-duration` and the chip `--rac-duration-fast`. The chip delete button inherits the radius frame by frame. The panel is left out: it is unmounted or collapsed while closed, so only a switch made while it is open snaps (its own `transition` list lives in base, add `border-radius` there knowingly).

## Option Content

What the trigger shows for a selected option: `valueAsOption` (config prop, default `false`).

- Text mode (default): the title and the chips show `option.name`. The name comes from the model's label chain. For a `<Option/>` without `label` / `name` / `id` / `value` it is the text found in its JSX (`getText` in `select.jsx`, a pure walk over the element tree; strings and numbers only). With nothing at all (an image only) the name is `texts.emptyOption`, and `optionRecord` warns once in development.
- Rich mode (`valueAsOption`): `optionContent(option, renderOption, selected)` in `utils.jsx` is the one resolver, shared with `OptionItem`: the option's own JSX wins, otherwise `renderOption(original, {selected: true, disabled})` for real data, otherwise null (the text is used). The content sits in `.rac-option-jsx`, like in the list.
- The option's `className` and `style` go onto the chip (`.rac-chip`) and, in single mode, onto the title element (`.rac-title`). `.rac-option` itself is not carried over (hover, highlight, selected tint and the checkbox belong to rows), so shared rules are written as `.rac-option-jsx, .rac-chip {…}`.
- Per-option `className` / `style` exist only on `<Option/>` (and per group only on `<OptGroup/>`). The model copies no `className` or `style` from array items or array groups: those fields are ignored, without a warning, so array data cannot style its row or its chip; `renderOption` styles only the content inside `.rac-option-jsx`.
- The model exposes `valueOption`: the selected option, or null when the title shows something else (`selectedText`, or no value, so a state text). `Value` uses it so the state texts never turn into option JSX. The title Collapse is keyed by `valueOption.id` in rich mode, by the text otherwise, so a changed selection still cross-fades.
- Gotchas: the chip cannot show different JSX from the row. Interactive content inside a chip conflicts with its click, swipe and long press. Each chip renders the content again, so heavy content costs more in big multiple selections. Like `renderOption`, `valueAsOption` is a config prop.

## Package Build

`vite.config.js` in the package root (`packages/react-animated-select/`). After any change here, check `dist/` and run `npm run check:pack` from the repo root (`scripts/checkPack.js`: an `npm pack --dry-run` that fails on a file outside the published list or a missing required one).

- Two formats, one output file per source module (`preserveModules`, `preserveModulesRoot: 'src'`): ES modules `dist/*.js` (entry `dist/index.js`, `import`) and CommonJS `dist/*.cjs` (entry `dist/index.cjs`, `require`). The package is `"type": "module"`, so the CommonJS files must end in `.cjs`: Node reads a `.js` file there as ESM and `require` fails with `exports is not defined`.
- `external` is a pair of regexps (`react`, `react-dom` and their subpaths), so `react/jsx-runtime` is imported, never bundled. `dist` imports only `react`, `react/jsx-runtime` and `react-dom`.
- `'use client'` is the first line of every output file (`output.banner`), before the injected CSS import.
- CSS: `vite-plugin-lib-inject-css` adds an `import './x.css'` to each ES module (`select.js` imports base and theme, `chip.js` imports `chip.css`), so bundlers load the CSS of the used modules by themselves; `"sideEffects": ["**/*.css"]` keeps it from being tree-shaken. The `cjs-output` plugin strips the CSS `require` from every CommonJS file, because plain Node and Jest without a CSS transform cannot `require` a stylesheet. The `style-css` plugin concatenates the emitted CSS into one `dist/style.css` (`@layer rac.base, rac.theme;`, then base, theme, chip: everything, chips included); CommonJS users, bundlers that skip CSS imported from JS and manual setups import `react-animated-select/style.css`.
- Types: `index.d.ts` serves `import`. The `cjs-output` plugin also emits a copy as `dist/index.d.cts` for the `require` condition: in a `"type": "module"` package TypeScript reads `.d.ts` as ESM types and rejects them for a CommonJS importer under `node16` resolution.
- npm ships only the `files` whitelist (`dist`, `index.d.ts`) plus `README.md`, `LICENSE` and `package.json`, which npm always adds. `README.md` and `LICENSE` are the canonical copies at the repo root: the package's `prepack` (`scripts/copyMeta.js`) copies them into the package folder, where the copies are gitignored. A package `.npmignore` would have no effect next to `files`, so there is none. `prepublishOnly` rebuilds `dist`.
