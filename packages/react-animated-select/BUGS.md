# Library bugs

Bugs found in the library, usually from the demo (cross-workspace rule 1 in [CLAUDE.md](CLAUDE.md)): an agent working on the demo reports a library bug to the owner and, unless it fixes it in place with the owner's approval or on a direct instruction, records it here. The fix belongs to the library (`src/`), never to the site. The library session reads this file, fixes, and marks entries done.

## Entry format

```md
### <short title>
- **Kind:** bug | api | docs | styles | perf | a11y | idea
- **Seen in:** demo section or file
- **Library:** file in `src/` or doc-key in `src/README.md`
- **Now:** what happens (steps if it is a bug)
- **Expected:** what should happen
- **Demo workaround:** none, or what the site does meanwhile (and where, so it can be removed)
```

Statuses: an entry sits in **Open** until the library ships the fix, then moves to **Done** with the version (`fixed in 0.7.6`). Once the demo is updated to that version and the workaround is removed, delete the entry.

- ~~Delete mode leaves a hole where the clear button and the arrow were, instead of giving the chips their space~~ — found by the owner (desktop Firefox capture, 2026-10-05) and fixed the same day, **to be confirmed on a device**: the previous entry fixed the jump by keeping the controls in the flow, but it handed their width to the row only when `deleteInline && !deleteAlways && removable` (`roomy`), on the argument that the other modes widen no chip and so need no room. That reads the feature backwards. The freed width is the *point* of delete mode on a narrow trigger — the controls are useless there, so the rows should spread into them — and in the two modes without `roomy` the controls faded while keeping their box, so the end of every row stayed empty for the whole mode.

  **Fix:** `roomy` is gone; `data-del-room` is set whenever delete mode opens and the controls measure more than 0. Two things had to follow. (1) The move needs its own FLIP: with overlay buttons or with `deleteAlways`, no chip changes width, so `dress` does not change, `Snapshot` takes no snapshot and the hold never runs — the room effect now reads the slot rects before it sets the attribute and FLIPs them after, and in the one mode where the chips *do* change width the dress effect's own FLIP replaces it (`flip` cancels any `rac-flip` on the element). (2) The release must not wait on an overlay button: `isBusy` is now called with `deleteInline`, not `true`, because only a button in the flow changes a chip's width; waiting on an overlay one held the room a full `duration` after the mode ended (release at +733 ms, now +111 ms). The controls also collapse by `scale: 0` now, not `opacity` alone, so they visibly shrink out of the way — a transform, so the layout width still leaves in one frame, which is what a real `width` transition got wrong in the first attempt. `--rac-room` is read from `getComputedStyle`, not `getBoundingClientRect`, because by then the scale is already running and a rect would hand back a shrinking room. Measured in headless Chromium (410 px viewport, 20 chips, `duration` 600), `.rac-value` 308 → 340 px in all three modes, chips re-wrapping into it: overlay 7 → 6 rows, `deleteAlways` 9 → 7 rows, `deleteInline` 7 rows held (its chips grow by their buttons, so the room is spent on them); biggest single-frame chip step 15.0 px (a smooth 600 ms re-wrap), no layout overflow, and every transition animated in both directions. - ~~The clear button and the arrow move the chip row width over `duration`, so the chips re-wrap mid-animation~~ — found by the owner (three videos, 2026-10-05) and fixed in two steps the same day, **to be confirmed on a device**. `.rac-clear` and `.rac-arrow` are plain flex siblings of `.rac-value` and delete mode unrendered them, so their `Collapse` moved the row width over `duration` while the chips were moving too. Entering: the hold's ghost is measured in the commit that starts the change, where the row was still two icons short, so it froze the narrow rows and the release wrapped them back (3 chips per row → 2 → 3, `IMG_4093`). Leaving was worse once entering was fixed: the controls **mount** at their natural width, and `useChipLayout`'s layout effects run before theirs (children before parents), so the FLIP was computed against the narrow layout, the `Collapse` then set them to 0 one effect later and the rows re-wrapped under the running transforms — chips flew past the trigger's edge (`IMG_4095`, 15 fps frames: chips scattered left and right of the trigger for ~3 frames, then converging). A third attempt was needed because taking them out of the flow on `[data-deleting]` fixed entering but not leaving: there the row narrows in the commit where delete mode ends, while the chips are still wide, so the layout really did collapse (measured in Chromium: 7 rows → 10 for one commit) and the FLIP was computed there — chip 17 of 20 got `translate(205.66px, -96px)` toward a row it never kept, which is the "chips fly past the screen" the owner saw (`IMG_4097`, and the same on desktop Firefox in responsive mode). `position: absolute` also moved both controls 8 px: the containing block of an absolute child is the root's **padding** box, a flex item sits in its content box.

  **Fix (final):** the controls never move and never leave the flow. `trigger.jsx` keeps them mounted in delete mode (`showClear` / `showArrow` have no `!deleting` term); `chip.css` only fades them (`.rac-select:is([data-deleting], [data-del-room]) :is(.rac-clear, .rac-arrow)`: `opacity: 0`, `visibility: hidden`, `pointer-events: none`), with the transition in `base.css` in one declaration for `rac-clear`, `rac-arrow` and `rac-group-arrow` so the arrow's `rotate` timing is not overridden (`visibility` transitions discretely but stays `visible` while either end is, so the fade reads both ways and the hidden state still leaves the accessibility tree). The width reaches the chips through `.rac-value`: `margin-inline-end: calc(-1 * var(--rac-room, 0px))` while `data-del-room` is set, so it grows by exactly what the controls occupy and overlaps them; the root keeps its width, so nothing can overflow. `useChipLayout.js` measures `--rac-room` (border box plus inline margins of the root's own `.rac-clear` / `.rac-arrow`) and sets the attribute in a layout effect placed **before** the dress effect, so the hold's ghost already sees the wider row; `settle` drops it right after it reads the `from` rects and before `restBreaks`, so the resting breaks and the FLIP see the final width and the chips make one move; a later effect covers the no-hold case with a `requestAnimationFrame` poll and its own FLIP. Measured in headless Chromium (410 px viewport, 20 chips, `duration` 600, long press in and tap out), before → after: `deleteInline` 205.4 px of chips outside `.rac-value` and a 226.5 px single-frame step → **0.0 px and 2.1 px**.
